# 做 MCP.Resource 之前，先把痛点摆清

这份文档**不写设计**。它只回答一个问题：**哪些事现在做不成、或者做得很别扭。**

工具该怎么切、叫什么名字，等这份清单定了之后再对着它定。

痛点分两种成色，分开标：

- **[真]** = 我**做不到**，或者只能靠"每次都记得手写一段"来做（会忘、忘了就出事故）
- **[绕]** = 我能做，但要绕、要写脚本、要多几次往返 —— 代价是时间和上下文

---

## 零、先划清"能力"和"痛点"的界限

上一版讨论里我犯过一个错：把"没有网络能力"当成了 http 工具的理由。**那是错的，而且现在不成立了。**

我当时手里已经有这些（同一个会话里实际用过/查过）：

| 能力 | 我有什么 | 备注 |
|---|---|---|
| 抓 URL 文本 | `web_fetch(url)` | HTML 会转成可读文本；JSON/纯文本原样 |
| 搜网 | `web_search(query)` | |
| **下载到磁盘** | `browser_download` | 返回 **saved path**，明说"这是任务拥有的文件，文件工具能读" |
| 完整浏览器 | `browser_open/navigate/snapshot/click/type/screenshot/preview/...` | 一整套真浏览器 |
| 任意命令行 | `pwsh` | `curl`、`tar`、`Expand-Archive`、`Invoke-WebRequest` 都能上 |
| 读文件（带范围） | `read_file`（offset/limit） | 按 UTF-8 解 |
| 写 / 改 / 批量改 / 删区间 | `write_file`、`edit_file`、`multi_edit`（原子批量）、`delete_range` | |
| **移动文件** | `move_file` | 专门强调"用它，别用 shell `mv`" |
| 列目录 / 找文件 / 搜内容 | `ls`（recursive）、`glob`、`grep` | |
| 符号 / 引用 / 诊断 | `code_index`、`lsp_definition`、`lsp_references`、`lsp_diagnostics` | |
| 记忆 / 历史 | `memory`、`remember`、`history` | |

**结论**：

> 网络访问不是痛点，本地文件读写也不是。
> 缺的是**访问的方式** —— 统一、可缓存、可引用、可回滚的那一层。

所以下面每一条痛点，**都必须能回答"我现有工具为什么做不到或做得别扭"**；答不上来的，就是重复造轮子，不该进设计。

## 一、七条母题

所有具体痛点归到七条母题下。**母题是设计要回答的问题，具体痛点是证据。**

| # | 母题 | 一句话 |
|---|---|---|
| **1** | **按需取一段，别把整份搬到面前** | 大文件 / 大页面 / 大压缩包 / 大日志，全在喊这一条 |
| **2** | **用一个短标识代替整份状态** | 缓存 key、内容指纹 cookie、介入令牌 —— 同一件事的三个名字 |
| **3** | **动作要可逆、要不覆盖别人** | 回收站、两段式确认、并发检测 |
| **4** | **别让我在每个域重学一套参数** | `read_file` 一套、`grep` 一套、`pwsh` 又一套 |
| **5** | **缺的是"访问方式"不是"访问能力"** | 统一 + 缓存 + 可引用 + 可回滚的那一层 |
| **6** | **有些资源要先执行 JS 才拿得到** | 无头浏览器；**执行代价越高，缓存越值钱** |
| **7** | **有些事 AI 不该独自做** | 人机验证、控制用户屏幕 —— 要"AI 知道 + 人授权" |

## 二、逐条痛点

### A. 读：定位 + 取片段（母题 1、4）

| # | 痛点 | 现在怎么绕 | 代价 | 成色 |
|---|---|---|---|---|
| A1 | **"在大文件里找一处，并读它周围"** | `grep` 拿行号 → `read_file` 带 offset 读 | **两次往返**；行号靠肉眼对齐 | [绕] |
| A2 | **编码不是 UTF-8 的老文件** | `pwsh` + `[Text.Encoding]::GetEncoding('gbk')` | `read_file` 按 UTF-8 解 → **中文全乱**；`pwsh` 又易踩引号/转义 | [绕] |
| A3 | **超大文件**（几百 MB 日志） | `pwsh Get-Content -TotalCount` / 逐段读 | 没有统一的"按段流式"手法；一次读全就爆 | [绕] |
| A4 | **正则匹配的上下文**（"匹配点附近 3 行"） | `grep` 给行 → 再 `read_file` 读上下文 | 同 A1 | [绕] |
| A5 | **"这个文件多大 / 什么时候改的 / 什么编码"** | `ls` 给 size；时间要 `pwsh` | 信息散在两个工具里 | [绕] |
| A6 | 目录里"哪个最近改过 / 这个目录多大 / 两个目录差在哪" | `pwsh` 排序、递归求和、`Compare-Object` | **每次现写脚本**；diff 尤其难 | [绕] |

> **A1 的实测证据**：这个会话里我核对 `docs/ZMS.MCP.Csharp.v4.md`（44 KB / 1010 行）时，
> 反复走的就是"`grep` 找行号 → `read_file` 按 offset 读"。"定位一处并读它周围"要 2–3 次工具调用。

### B. 写：可逆，且不覆盖别人（母题 3）

| # | 痛点 | 现在怎么绕 | 代价 | 成色 |
|---|---|---|---|---|
| B1 | **删除不可逆** | 每次手写 `[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory(..., 'SendToRecycleBin')` | **长、易忘**；默认的 `Remove-Item` 是硬删。**这是唯一一个"我可能忘，忘了就不可逆"的地方** | **[真]** |
| B2 | **并发写同一份文件** | 没有机制。`edit_file` 的 `old_string` 唯一性**碰巧**能挡住"内容变了"，但不说"是别人改的"；`write_file` 整份覆盖**完全挡不住** | 多 agent / 多会话同时改 → 静默丢改动 | **[真]** |
| B3 | **"我读到的"和"我写回去的"之间被人改过** | 我没有 cookie 那套（Csharp 有，因为它做了） | 覆盖别人的改动，**而且不会知道** | **[真]** |

> B2/B3 是同一条的另一面：**"用短标识记住我读的是哪一版"**（母题 2）。
> Csharp 用 `SHA256(内容)[..16]` 做，Resource 该用同一套口径 —— 两套并存会让 AI 学混。

### C. 网络：缓存与渲染（母题 1、2、5、6）

| # | 痛点 | 现在怎么绕 | 代价 | 成色 |
|---|---|---|---|---|
| C1 | **同一个 URL 读两次要跑两遍网络** | 无。`web_fetch` 每次重下 | 慢、可能失败、浪费 | **[真]** |
| C2 | **内容直接进上下文** | 无。200 KB 的 JSON 就那样塞进来 | 上下文被一份数据占满 | **[真]** |
| C3 | **跨会话复用** | 做不到 | 新会话要重新拿一遍 | **[真]** |
| C4 | **"下载下来，只读其中一段"** | `browser_download` 给了 saved path → 然后还是得 `read_file` **全读** | 缺"**给 key + 按需取片段**" | **[真]** |
| C5 | **限流** / 别把站点打死 | 无 | 批量抓 = 打对方 | [绕] |
| C6 | **缓存过期** | 没有概念（草稿说 10 分钟 —— 那**过期后**怎么办、怎么**知道**它过期了） | 要么永久错，要么永远重取 | **[真]** |
| C7 | **动态 JS 渲染** | 只能用 `browser_*` 手动导航 + 取 snapshot | **每个页面一套动作**；也没有"渲染版 fetch" | [绕] |
| C8 | **Cloudflare 之类的整站拦截** | 拿回来一个 `Just a moment...` 页面 | ⚠️ **最糟的情况**：如果工具静默返回挑战页 HTML，AI 会以为"这网站就长这样"，然后开始分析那个挑战页 —— **这比失败更糟** | **[真]** |

> **C1~C4、C6 是同一条母题的不同外壳**：缓存的真正价值不是"存下来了"，而是
> **"AI 在上下文里只留一个 key，而不是一整份内容"** —— 跟 `edit_project_metadata` 的 cookie 是同一个思路。
>
> **C7 和 C8 是一条**：现代网页 = JS 渲染 + Cloudflare 前置。
> 渲染很贵（起浏览器、等挑战、跑 JS），**所以"渲染结果更该被缓存"** —— 执行代价越高，缓存价值越大。

### D. 远程：FTP（母题 4、5）

| # | 痛点 | 现在怎么绕 | 代价 | 成色 |
|---|---|---|---|---|
| D1 | **访问 FTP** | `pwsh` 写 `FtpWebRequest` | 老 API、别扭；**中文文件名 / 被动模式 / 编码**全是坑 | **[真]** |

> 这是清单里**唯一一个"我完全没有"**的访问能力。SFTP/SCP/WebDAV 建议不做 —— 再加协议是把口子越开越大。

### E. 压缩包（母题 1、5）

| # | 痛点 | 现在怎么绕 | 代价 | 成色 |
|---|---|---|---|---|
| E1 | **不解压就看包里一个文件** | 解压到临时目录再读 | 整份展开；大包很贵 | [绕] |
| E2 | **非 zip 格式**（tar / tgz / nupkg） | zip 用 `Expand/Compress-Archive`，tar/tgz 用 `tar` | 手段不统一；nupkg 实际是 zip | [绕] |
| E3 | 包内写 / 包内删 | 解压 → 改 → 重打 | zip 做"包内写"本来就要**重写整包** | [绕]，**建议砍掉** |

> **E1 和 C4 是同一条**：*"别把整份展开，按需取一段"* ——
> `zip://a.zip!/entry`、`file://x.txt?offset=`、`http://...` 三者同构。
> **如果这个判断成立，"缓存"就不该是 http 专属，而是一个通用的"取片段"层。**

### F. 人机验证与"AI 不该独自做的事"（母题 7）

| # | 痛点 | 说明 | 成色 |
|---|---|---|---|
| F1 | **人机验证**（Cloudflare Challenge / Turnstile、滑块、点选） | 它的**设计意图就是"证明对面是人"**。agent 不是人 → **不存在"正确地通过它"** | **[真]** |
| F2 | **"需要控屏的操作"没有授权机制** | 弹浏览器 = 控制用户屏幕。**还原难度不是"大"，而是"根本不该由 AI 独自做"** | **[真]** |

**定的方向（用户已明确）**：

> **有操作的。把浏览器拿出来弹框，让用户走这个验证。
> 当然，需要 AI 知道做什么并经过用户授权。**

也就是：

- ❌ **不做**：打码平台、破解挑战参数、stealth 反指纹、代理池轮换 —— 那是**对抗对方明确表达的意图**
- ✅ **要做**：识别到拦截 → **明确报"这是拦截，不是页面内容"** → 请求人介入 → 人过 → 会话交回给"要用它的那个进程"

**一个技术硬约束**（选错了会白做）：

> **验证的产物（会话/cookie）必须落在"要用它的那个进程"手里。**
> 所以**不能**让用户去系统浏览器里过验证 —— 那样 cookie 在别人那儿，抓取还是失败。
> 正确做法是**服务自己用 persistent context 起一个可见浏览器**，宿主只负责把它呈现出来。

### G. 贯穿性的观察

七条母题里，**1、2、6 其实是同一件事的三种说法**：

- **1** 是**目标**（只取我要的那一段）
- **2** 是**手段**（用一个短标识指向它）
- **6** 是**为什么更值钱**（拿到的代价越高，这个标识越重要）

而 **3、7 是同一类**：**这个动作危险吗 —— 危险的定义是"还原难度"，而"要人参与"是它的极端形态。**

## 三、明确**不**该由 Resource 管的

免得把域划歪（这些我在现有工具里都有，或者属于别的项目）：

| 事 | 归谁 | 为什么 |
|---|---|---|
| 执行进程 / 跑脚本 / 收发 JSON-RPC | 执行域（`pwsh`） | 不是"资源访问" |
| **JSON / XML / YAML / TOML / INI 的解析** | `ZMS.MCP.Structured` | **跨项目** —— 这是你指出的那道裂缝 |
| C# 符号语义（引用 / 改名） | `ZMS.MCP.Csharp` | |
| 本地文件的读 / 写 / 替换 / 批量替换 / 移动 | **已有内置工具** | 重复造轮子 |
| 网络访问本身 | **已有**（`web_fetch` / `browser_*` / `pwsh`） | 重复造轮子 |

**照这个表，旧草稿（`todo/Resource.md`）里"本地文件 9 个操作 + 目录 4 个操作"基本可以砍掉** ——
它们不是痛点，是"内置工具的加料版"。真正站得住的只有：
**缓存、渲染、FTP、回收站删除、压缩包的按需取用、以及 F2 那条"人授权"的机制**。

## 四、还没想清的（留给设计阶段）

1. **"缓存"到底属不属于 http 专属？**（第 E1 条那个假设：它可能是通用的"取片段"层）
2. **`json@` 这一层怎么跨项目接** —— 分层（Resource 只取字节）/ 客户端编排 / 各做一份
3. **并发检测做到哪一档** —— 只做"内容指纹对不上就拒绝"，还是要到"谁改的"
4. **渲染的依赖怎么带** —— Playwright 复用系统 Edge/Chrome（不下载浏览器）算不算可接受的重依赖
5. **工具粒度**（上一轮列过三档：scheme 当工具 / method 当工具 / 两个万能工具）——**等这份痛点定了再定**
6. **缓存的生命周期** —— 谁清理、什么时候过期、跨会话存哪
