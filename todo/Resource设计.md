> 每条设计尽量能指回母题；指不回去的，就是没理由存在的东西。

---

## 一、总纲

1. **所有工具的结果都进缓存** —— 读、写都存；但**写工具的结果不会被"命中返回"**（见 §三）
2. **一个 cache 工具**访问缓存：列出 / 读取 / 落盘
3. **一个入口**：`cookie` 决定走哪个协议 —— 空 = 本地，有 = 那个会话
4. **cookie 是会话句柄，仅内存保存** —— 里面记住 uri / 端口 / 用户 / 密码，之后不必再填
5. **破坏性操作两段式**（无 cookie 时先返回"会发生什么"+令牌）
6. **失败必须写明原因**，不能静默（尤其"被拦截"与"没内容"必须分开）

## 二、工具清单

### 2.1 会话（FTP）

```
ftp_login(host, port=21, user="", password="")  → cookie
ftp_logout(cookie="")
```

**`ftp_logout`**

- 带 cookie：只注销**你自己**那个会话
- 不带 cookie：**全部注销**，并报告"**注销了 N 个连接**"
- **不知道 cookie 时，这是唯一允许的动作**

> **为什么这么设计**（用户原话）：
> *"这个本意就是隔离的。如果你确认注销你的就带 cookie。如果你不知道 cookie，也不让你穿透到别人的权限里面去。
> 这样会无用户名密码就操作未知路径。所以不知道 cookie，只能进行注销。"*
>
> 也就是说：**越权从"能力层面"堵掉**，而不是靠调用方自觉 —— 跟工作空间边界是同一种做法。

### 2.2 资源操作（一个入口，cookie 决定协议）

```
list(path,   cookie="", depth=3, limit=20, type="", meta="", regex="")
read(path,   cookie="", skipline=0, takeline=0, offset=0, length=0, encoding="", regex="")
write(path,  content, cookie="")
delete(path, cookie="")
move(src,    dst, cookie="")
```

| cookie | 走哪个协议 |
|---|---|
| 空 | **本地文件** |
| 非空 | **那个 FTP 会话**（连接信息在 cookie 里） |

**本地那一侧不重写逻辑** —— 转调现有能力即可，差别只有一个：**它带缓存**（内置工具没有）。

### 2.3 网络

```
http(url, method="GET", head="", body="", path="", cache=true)
```

| 参数 | 语义 |
|---|---|
| `path` 空 | 取内容（进缓存，返回 cookie） |
| `path` 有值 | **下载到该路径** |
| `method` | GET / POST / PUT / PATCH / DELETE / HEAD / OPTIONS |
| `cache` | `true`（默认）= 允许命中缓存；`false` = **真去拿**，并把新值**覆盖**进缓存 |

### 2.4 缓存

```
cache_list()
cache_read(cookie, path="")
```

| 用法 | 行为 |
|---|---|
| `cache_list()` | 列出条目：**调用时间 / 工具 / 参数 / cookie / 大小**。**不展示 body** |
| `cache_read(cookie)` | 读缓存内容 |
| `cache_read(cookie, path=...)` | **把缓存写磁盘** —— 之后才能交给别的工具（`json` / `structured_read`）去读 |

**用法三就是 `json@` 的替代品**：`json@` 被拆掉之后，这是跨项目最干净的接法 ——
这边只负责"**把字节交出来**"，解析归 `ZMS.MCP.Structured`。

## 三、缓存规则

| 项 | 规则 |
|---|---|
| **失效** | **纯时间，7 天** |
| **谁进缓存** | **所有工具**的结果（读、写都存） |
| **谁会被命中** | **只有读工具**。写工具的结果**存下来供回溯，但绝不命中返回** |
| **命中时** | 返回里**必须写明"这是缓存"**；不命中时写明**"这不是缓存"** |
| **不命中时** | 新值**覆盖**写入缓存 |
| **`cache_list`** | **不展示 body**（只元数据） |

> **为什么写工具不命中**：`confirm_draft` 若被命中，会返回"已落盘"，而实际什么都没发生 ——
> 这比失败更糟。这条是"**别让 AI 以为自己做了什么**"的直接应用。

> **7 天是纯时间失效**：意味着 7 天内输入变了它也不会知道。
> 所以"**返回必须写明这是缓存**"不是礼貌，而是**这条设计成立的前提** —— AI 看到那句话才有机会判断"我要不要 `cache=false` 重跑一次"。

## 四、限流（**总量配给，不是限速**）

| 项 | 值 |
|---|---|
| 初始额度 | **10 MB** |
| 恢复速率 | **每分钟 +1 MB** |
| 上限 | **10 MB**（攒不满更多） |
| 性质 | **总量**：超过额度就**不给下载**（不是把速度压慢） |
| 实现 | .NET 自带（`System.Threading.RateLimiting` 的令牌桶） |
| 前置 | **必须预先知道资源大小** |

**"预先知道大小"怎么做**：

1. 先发 **HEAD**（或 `Range: bytes=0-0`）拿 `Content-Length` / `Content-Range`
2. 大小 **≤ 当前额度** → 下载，扣额度
3. 大小 **> 当前额度** → **elicitation 征求用户同意**（"这个文件 180 MB，当前额度 10 MB，要下吗？"）
   - MCP 协议确实有这个能力（`elicitation`）：服务端向**用户**提一个表单/确认，客户端负责呈现
4. **拿不到大小**（chunked / 不支持 HEAD / 服务器不报） → 按剩余额度**边下边数**，超了就停下并征求同意
   - **不能**因为"不知道大小"就放行 —— 那等于额度形同虚设

## 五、会话与隔离

```
ftp_login(...)  → cookie  ── 仅内存保存（uri / 端口 / 用户 / 密码）
                            不落盘、不进缓存 body、不在 cache_list 里出现明文
```

- **cookie 不带密码进日志**：`cache_list` 的参数列必须对 `password` / `Authorization` 之类的字段**打码**
- **不带 cookie 只能 `ftp_logout("")`**：这是"隔离"的落点，也是"无凭据不碰未知路径"的落点

## 六、待定（不定就没法开工的几件事）

| # | 问题 | 我的建议 |
|---|---|---|
| 1 | **缓存放哪、多大** | 跟 Csharp 同口径用 sqlite 存 `%LOCALAPPDATA%`；设**总量上限**，超了淘汰最老的（FusionCache 自带这个能力）。7 天 TTL + 所有工具，量一定会涨 |
| 2 | **限流按站点还是全局** | 按**站点**更准（"别把对方打死"本来就是按站点的）；全局则简单。建议按站点 |
| 3 | **FTP 下载要不要也限流** | 建议同一套配额（理由相同） |
| 4 | **本地那一侧做到多深** | 只做"转调 + 加缓存"（薄）？还是也要 `?offset=` / `#regex` 那套（厚，等于重写读逻辑，痛点 A1/A4） |
| 5 | **缓存 key 怎么算** | 工具名 + 规范化参数；会话类（FTP）的 key 要不要含 cookie，会决定"换条连接还能不能命中" |
| 6 | **两段式在哪些工具上** | 破坏性操作 = 删除 / 移动（目标已存在）/ 覆写 / 过大下载征求同意 —— 是否都用同一个令牌机制 |
