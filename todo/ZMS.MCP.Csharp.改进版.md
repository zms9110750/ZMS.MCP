# ZMS.MCP.Csharp 工具手册 v4

这份手册以**实机调用结果**写成：每个工具的参数取自运行时 schema，返回值示例是实际调用回来的原文（不是从代码推断的）。共 **20 个工具**。

> 与 v3 的主要差别：
> 新增 `rename_symbol`（只有语义层做得到的那件事）；`symbols` 新增**四个"要不要列出"的信息开关**（文档注释 / 特性 / 被引用 / 实现），原来的 `read` 被它们收编；[^16]
> `symbols` 的成员寻址语法统一、骨架不再按文件切；`type` 里的 `D` 从"文档注释"换成"委托"；
> `stage_draft` 的路径语义改为"`typePath` 指向什么就加什么"（指向类 = 改成员，指向命名空间 = 加类）；
> 新建类型的壳不再写死 `public class`；补 `partial` 的位置修正；匹配不上时报错而不是当"新增"；
> 拟定全程在内存、每条改动立刻编译；cookie 改成按语义算、落盘前按类比对；MSBuild 求值缓存只认"文件列表"。
>
> 逐条差异都在脚注里，编号对应《Csharp工具痛点》里那一条。

## 约定

- 参数类型用 C# 可空语法：`:string` = 必填；`:string?` = 可空（"没给"与"给了空串"等价）。
- `integer` / `boolean` 不可为 null，但通常有默认值。
- **所有工具的错误都是同一种文本形态**：`Error: <异常消息>`。需要外部命令的工具（`dotnet add/remove/sln ...`）在命令非 0 退出时把命令行输出整段带回。
- `csprojPath` 统一解析：绝对路径（存在即用）；否则当成**项目名**，从当前目录向上找解决方案、在其中找唯一同名项目，重名时要求给完整相对路径。
- 需要外部命令的写入工具（解决方案编辑、装包/删包、迁移）**不进任何事务**：立刻改盘、不可回滚。
- **符号寻址只有一套语法**：`命名空间.类型.成员`，方法带**无空格**参数表。`symbols`、`stage_draft`、`rename_symbol` 全都走同一个解析器，`symbols` 列出来的写法可以直接抄给其它工具。[^1]
- **编译器项目进度的三种状态**要分清：`按需加载`（首次求值，秒级）/ `命中缓存`（磁盘没变，毫秒级）/ `重新求值`（磁盘变了）。每个工具的输出里都会标明这次是哪一种。[^2]

## 五、符号查询

### 14. 符号 `symbols`

**一个工具、两层开关**：先选**列哪些符号**（筛选），再选**每个符号列出什么**（信息开关）。

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `csprojPath` | `:string` | 要能解析到项目文件（**必填**） |
| `path` | `string?` | 空 = 列出符号；`Ns.Type` = 只列这个类型的成员；`Ns.Type.Member(...)` = 直接读这一个成员（给签名 + 文件 + 行号 + 源码） |
| `type` | `string?` | 字母取自 `NCSITPFEMD`：`N` 命名空间、`C` class、`S` struct（含 enum）、`I` 接口、`T` = `C`\|`S`\|`I`、`P` 属性、`F` 字段、`E` 事件、`M` 方法、`D` 委托；空 = 全部 |
| `modifier` | `string?` | 修饰符过滤，见下 |
| `argsList` | `string?` | 参数类型过滤（消歧重载），见下 |
| `nameFilter` | `string?` | 完全限定名的子串过滤，见下 |
| `documentation` | `boolean` | 默认 `false`；`true` = **把每个符号的 XML 文档注释也列出来** |
| `attributes` | `boolean` | 默认 `false`；`true` = **把每个符号的特性（attribute）也列出来** |
| `references` | `boolean` | 默认 `false`；`true` = **把"谁引用了这个符号"也列出来**（给的是符号，不是位置 —— 见下） |
| `implementation` | `boolean` | 默认 `false`；`true` = **把每个符号的实现体也列出来** |

**前四个是筛选（列哪些），后四个是信息开关（每条列出什么）。** 两层正交：先按 `type` / `modifier` / `argsList` / `nameFilter` 圈范围，再用后四个决定每条带多少内容。四个开关可任意组合 —— `path='Ns.Type'&implementation=true&references=true&attributes=true` 就是"这个类型的成员，连同特性、实现体、谁在用它，一起给我"。[^16]

> `type` 的字母 `D` 在 v3 里是"只列带文档注释的"（一个筛选）。那个能力现在归 `documentation` 开关，所以 `D` 空出来了 —— 回收给**委托**。[^24]

**三个筛选参数各自怎么工作**：

- **`modifier`** —— 逗号分隔，**每一个都要满足**（是 AND，不是 OR）。写 `'public,static'` 就是"既 public 又 static"；想表达"public 或 static"得查两次。认的写法就是源码里那些词：`public` / `internal` / `protected` / `private` / `static` / `const` / `abstract` / `readonly` / `virtual` / `override`。
- **`argsList`** —— 逗号分隔的**参数类型**，只对**方法**有意义，而且是**精确匹配**：给了 `'string,int'`，只有参数表**恰好**是 `(string, int)` 的方法留下；`(string)`、`(string, int, bool)` 都不留。它用来**消歧重载**，不是"包含这些参数"。
- **`nameFilter`** —— 对**完全限定名**（`命名空间.类型.成员`）做**大小写不敏感**的**子串**匹配。所以 `'Log'` 会同时命中 `Logging`、`Logger`、`MyLog` —— 它是"缩小范围"，不是"精确定位"；要精确点到某一个用 `path`。

（筛选项之间是**并列**的，同时给就一起生效。）

**实测输出 A**（列方法，`type=M`）：

```
# X:\temp\zms-tool-drill\Demo\Demo.csproj
- TFM: `net10.0` | 符号: 3 | 过滤: type='M' modifier='' args='' nameFilter=''
- 项目状态：命中缓存（磁盘未变）

## Demo.Class1
  - `public int Add(int,int)` (method) — Class1.cs:5
  - `public int Sub(int,int)` (method) — Class1.cs:10
  - `public string Pick(string,string)` (method) — Class1.cs:15
```

- **列出的就是可以抄的 `memberName`**：无空格参数表、参数类型用**源码里那个写法**（`string` 不写成 `System.String`）。[^1]
- 可空引用类型不进参数表：`string?` 与 `string` 是**同一个签名**，两边都认。[^5]
- 数组写成 `string[]`（`string` + `[]`），不写成 `System.Array`。[^5]
- 字段和嵌套类型**用裸名**（不带参数表），和 v3 一致。[^1]

**实测输出 B**（读一个成员）：


- **partial 类按"符号"给全貌**：一个符号有几处声明就列几处，不再按文件切出几份残缺视图。[^6]

- **`references=true` 给的是"哪个类的哪个成员"，不给文件位置。** 要位置就**再查一次那个符号**（`path='Ns.Type.Member(...)'` 会一并给出文件与行号）—— 位置是另一个问题，不塞进引用列表里。[^23]

### 15. 重命名符号 `rename_symbol`

**只有语义层做得到的第一件事。** 改名一个符号，把**引用它的每一处**一起改。

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `cookie` | `:string` | `track_project` 返回的追踪 cookie（**不要给 csprojPath**） |
| `memberPath` | `:string` | 要改名的符号，写法同 `symbols` |
| `newName` | `:string` | 新名字（不含类型前缀，就是个标识符） |

**它不自己写盘 —— 它往拟定里加一条改名。** 落盘统一走 `confirm_draft`，和 `stage_draft` 是同一套流程：同一次拟定里可以既有"改成员实现"又有"改名"，预检时一起编译、一起报诊断，落盘时一起写。[^17]

**实测输出**（拟定之后、落盘之前，先把"会改哪几处"摆出来）：

```
# 拟定已更新
- 项目：...\Demo\Demo.csproj
- 符号：Demo.Class1.Add(int,int)
- 本次：改名（Add → AddUp）
- 会改 7 处，分布在 3 个文件：

## Demo/Class1.cs
- 12:8  声明
- 30:20 调用

## Demo/Program.cs
- 8:18  调用

## Demo/Class1.Tests.cs
- 14:22 调用
- 40:9  调用
- 51:15 调用
- 62:30 调用

# 不会碰（名字相同但不是它）
- Demo/Class2.cs:9  另一个类型里的 Add(int,int)
- Demo/Class1.cs:77  方法体里字符串 "Add"
- Demo/Class1.cs:80  注释里的 Add

- 拟定条数：2
- 落盘许可（若有）已作废：要落盘请重新 confirm_draft（不带 cookie）做预检。
```

**"不会碰"这一节是它存在的理由**：文本替换会把上面那三行一起改掉，语义改名不会。[^7]

它和 `stage_draft` 的差别只在"改什么"：一个改实现体、一个改名字，但**记进拟定、预检、落盘、作废许可**这套行为完全一样。所以：

- 一条改名也要**先 `track_project`** 拿 cookie。
- 拟定里同时有改名和多处成员改动时，**取消/放弃也只有一个口子** —— `confirm_draft` 落盘，或者重新 `track_project` 清掉。
- 跨项目、跨 `#if` 分支一起改（改的是符号，不是文本）。

## 六、拟定流程（cookie）

一条完整的写代码流程：`track_project` 建立追踪 → `stage_draft` / `rename_symbol` 累积改动 → `confirm_draft` 预检（编译并汇报诊断）→ 带落盘 cookie 再 `confirm_draft` 落盘。

这一节的几条规则是整条链的地基：

1. **拟定全程在内存里做，不碰磁盘。**[^18] `track_project` 之后项目加载**一次**（拿到一份编译），之后每一次 `stage_draft` / `rename_symbol` 都只是在这份编译上做**内存替换** —— Roslyn 的编译对象是不可变的，改一次得到新的一份，没动过的语法树共享。磁盘上的 `.cs` 从头到尾没被读过第二遍，更没被写过。
2. **每加一条改动就编译一次，当场回报"这条改动引入了什么诊断"。**[^19] 一条一条来，错在哪一条立刻就知道，不用攒一堆再回头找。
3. **报的是"新增 / 消失的诊断"，不是"有没有诊断"。** 因为拟定是**串行**的，中间态本来就可能不完整（先加接口成员、再加实现，第一步天然有错）—— 报绝对的对错会一直吵，报"你这一步让什么变多了 / 变少了"才有信息量。
4. **落盘那一刻才重新看磁盘 —— 而且比的是"类"，不是文件，也不是整个项目。**[^22]
   `confirm_draft` 落盘时重新求值、重新读 `.cs`、重新编译，然后**以类为单位**比对"快照时"和"现在"，得到一张"**哪些类变了**"的表：

   - 比**文件**更细：一个文件里放了三个类，别人只动了第二个 —— 只有第二个算变。拟定改的如果是第一个类，照样落盘，别人在第二个类里的改动原样留着。
   - 比**整个项目**更准：不用为了"有没有人动过手"把无关的类也算进来。
   - 一个类的指纹 = 它所有成员的**符号指纹**（见下节）按成员名排好再哈希。

   判定：

   | 变了的类 ∩ 拟定涉及的类 | 结论 |
   |---|---|
   | 空 | 落盘，而且**只替换拟定涉及的那几个成员**（基于磁盘最新文本做定点替换），文件其余字节一字不动 |
   | 非空 | 冲突：列出**是哪几个类变了**，要求重新拟定，或在 `select_draft` 里明确接受现状 |

   落盘用"定点替换"而不是"整份重新生成"，是**语义比较**（见下节）的必要配套：语义没变的改动（别人只改了注释、排版）不会被判成冲突，那就更不能在落盘时把它们抹掉。
5. **落盘之后，基线按落盘后的现状整体重算。**
6. **拟定一变，落盘许可立刻作废**，必须重新预检。

### cookie 都是当场算出来的

三个 cookie 都是**哈希**，不是"随机串 → 状态"的映射条目：[^20]

| cookie | 谁给的 | 算的是什么 |
|---|---|---|
| **追踪 cookie** | `track_project` | `SHA256(项目路径)`。它只需要回答"这是哪个项目"。**但**"拿 cookie 反查项目"还需要点东西：要么把路径一起带在 cookie 里，要么留一张"路径 → 项目"的小表 —— 不必存整份快照。 |
| **符号指纹** | —— | cookie 的基本单位，见下 |
| **落盘 cookie** | `confirm_draft` 预检 | `SHA256(拟定的规范文本 + 预检时"类级"状态指纹)`。落盘时重算一遍，就能验证"拟定没变过、项目也没变过"，不靠"我保证只发过一次"。 |

### 指纹算的是语义，不是文本 —— 语义不变，指纹必须一致

**这是硬要求。**[^21] 所以指纹既不能建在源码文本上，也不能只建在语法树上，要建在 Roslyn 的**操作树**（`IOperation`）上 —— `SemanticModel.GetOperation(node)` 拿到的操作树里，**语法糖已经拆掉了**，而且引用的是**符号**不是名字：

| 这几种写法 | 语法树 | 操作树 |
|---|---|---|
| `List<int>` / `System.Collections.Generic.List<int>` / `using L = …; L<int>` | 都不同 | **同一个** `IObjectCreationOperation`，`Constructor` 是同一个符号 |
| `this.Foo()` / `Foo()` | 多一层 `MemberAccessExpression` | **同一个** `IInvocationOperation`：`TargetMethod`、`Instance` 都一样 |
| `int` / `Int32` / `System.Int32` | 不同 | **同一个**符号 |
| `@class` / `class` | 不同 | **同一个**符号 |
| `(a)` / `a` | 不同（多一层括号） | **同一个**操作 |
| 注释、空白、换行、`using` 的先后 | 都不同 | **压根不是操作**，不参与 |

符号自己用 `DocumentationCommentId.CreateDeclarationId(符号)` 取规范名 —— 它也是从**符号**算出来的，所以天然与 using / 别名 / 简称无关：`Add(int a, int b)` 永远是 `M:Demo.Class1.Add(System.Int32,System.Int32)`。它是**可逆**的（`DocumentationCommentId.GetSymbolsForDeclarationId` 能反查），顺手还能校验。

```
一个符号的指纹 = SHA256(
      符号的规范 ID
    + 操作树（递归）：每个节点记 OperationKind + 它引用的符号 ID + 常量值 + 类型
    + 一层直接引用到的符号 ID（排序后）
)
一个类的指纹   = SHA256( 它所有成员的符号指纹，按成员名排好 )
项目的状态指纹 = SHA256( 它所有类的类指纹，按类名排好 )
```

（一个细节：隐式接收者和显式 `this` 的 `ReferenceKind` 可能不同 —— `ImplicitReceiver` vs `ContainingTypeInstance`。规范化时把这一处归一。）

**归一不到的那一类**：`IOperation` 拆的是**语法糖**，拆不了**程序等价** ——

| 写法 | 为什么不归一 |
|---|---|
| `a + 0` vs `a` | `IBinaryOperation` vs `ILocalReferenceOperation`（代数化简） |
| `for` vs `while` | `IForLoopOperation` vs `IWhileLoopOperation`（控制流等价） |
| `x += 1` vs `x = x + 1` | `ICompoundAssignmentOperation` vs `ISimpleAssignmentOperation` |
| 无依赖的两行交换 | 语句顺序等价 |
| 局部变量改名 | 符号确实换了 |

判定"两段代码是不是同一个程序"没有有限规则（一般不可判定），所以这里只能**保守**：**误报（当成变了，让你重看），但绝不漏报**。

换来的好处是**幂等**：同一份语义永远算出同一串。于是进程重启、agent 换会话，拿着同一个 cookie 回来照样有效 —— cookie 是**内容的名字**，不是某个进程内存里的句柄。

### 16. 追踪项目 `track_project`

同 v3（含"只存 hash、不存文件快照"的说明）。新增一行：输出的项目状态里会说明这次的编译来自缓存还是重新求值。[^2]

### 17. 拟定改动 `stage_draft`

参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `cookie` | `:string` | `track_project` 返回的 cookie（**不要给 csprojPath**） |
| `typePath` | `:string` | 指向**类** → 改它的成员；指向**命名空间** → 在那个命名空间下**加一个类**（见下） |
| `memberName` | `:string` | 成员名；跟已有重载撞名时带参数表消歧。**`typePath` 指向命名空间时忽略它** |
| `content` | `:string` | 要写进去的代码 —— 是**成员**还是**类声明**，由 `typePath` 指向什么决定。[^9] |
| `before` | `string?` | 插入位置参照（加成员时用） |

**`typePath` 指向什么，就加什么**（这是与 v3 差异最大的地方）：

| `typePath` 指向 | `memberName` | `content` 是什么 | 含义 |
|---|---|---|---|
| **一个类**（已存在） | 给名字 | 该成员的完整代码 | 加/改**这个类的一个成员** |
| **一个命名空间** | 忽略 | **该类的完整声明**（含修饰符、特性、基类、`partial`）[^10] | **在那个命名空间下加一个类** |

**加成员时 `memberName` 是"新成员的名字"，不是一条已有路径** —— 成员还不存在，所以工具不要求它"先能被定位到"，也不要求你先把参数表写全（只有跟已有重载撞名时才需要带参数表消歧）。[^25]

**整类替换**走另一条路：`typePath` 指向已存在的类、`memberName` 给**空串**、`content` 给替换后的**完整类体**。

```

- 符号：（新）Demo.Tools.DemoTools

- 消失：0 条（错误 0 / 警告 0）

- 落盘许可（若有）已作废：要落盘请重新 confirm_draft（不带 cookie）做预检。
```

（第二条拟定如果引用了还不存在的类型，这里就会当场多出 `CS0246` —— 而你刚写的就是这一条。）[^19]

而它在 `.cs` 里写出来的就是**你给的那段声明本身**：给 `[McpServerToolType] public static partial class DemoTools` 就写这个，不会再套一层 `public class`。[^10]

- 拟定改动会**累积**（重复调用叠在同一个拟定上），并**作废已有的落盘许可** —— 必须重新 `confirm_draft` 预检。
- 给**已存在的类**加成员时，如果那个类不是 `partial`，会自动补上；补的位置是**所有修饰符之后**，`public sealed partial class` 合法，不会拼出 `public partial sealed class`。[^12]

```
- 消失：0 条（错误 0 / 警告 0）

## 预检查
- ✅ 无占用、无冲突

- 落盘 cookie：`6b0f9a29-...`（传回来才落盘；每次预检换新，旧 cookie 立刻失效）
```

**实测输出 B**（落盘）：

```
## 已落盘
- ...\Demo\Tools\DemoTools.cs
- 编码：按各文件原编码写回（新建文件 UTF-8 无 BOM）
- 格式化：已对本次改动的文件跑 dotnet format
- 项目状态：**需要重新求值**（本次改动动了磁盘；下次调用会重跑一次 MSBuild 求值）
- 追踪继续，基线已按落盘后的现状整体重算。
```

- **它自己会声明"下次要重新求值"** —— 因为落盘真的改了 `.cs`，那份编译快照必须重拍，否则刚落盘的代码在本次会话里看不见。[^2]
- 但**只改内容（没增删文件）时不会强制重跑求值**：MSBuild 求值的缓存指纹只认"源文件路径集合"，内容变化交给"每次都重读文件"的那一层（几十毫秒）。省下来的是每次改完文件后那几秒。[^13][^14]
- 预检查不通过（文件被占用 / 有未解决冲突）会拦下来，不落盘。
- 落盘时跑的 `dotnet format` **会加载并执行目标项目引用的 analyzer 程序集**。如果那个项目引了不信任的包，这里就是一条执行外部代码的路径；输出的"格式化"一节会写明本次实际加载了几个 analyzer（0 个也写出来）。[^15]

[^3]: **无差异**：`scan_projects`、`view_project_or_solution` 与 v3 一致。（v3 里"不跟随 `ProjectReference` 展开"、"不做 MSBuild 求值"这些边界都保留。）

[^6]: **差异**：v3 讲"分部类会把全部声明位置列在同一行"，但按文件给结构时一个 `partial` 类会得到好几份不完整视图。v4 按符号给全貌。对应 §7（skeletoken-mcp 同类问题）与 §3（`partial` 相关的坑）。

[^7]: **新增工具**：v3 没有改名能力，只能文本替换 —— 于是同名但不同的符号、注释里的名字、字符串字面量都会被误改。`rename_symbol` 走 Roslyn 的语义改名。见《Csharp工具痛点》§6 的判据表。

[^8]: **修 bug**：v3 没有引用查询。这里补上的引用查询会遍历 `GlobalStatementSyntax` —— 顶层语句里调用的方法才算得上（同行各家都漏过这一类，见 §7 之 1）。

[^9]: **差异**：v3 的 `content` 恒为"**类体**"（不是类型声明、不能带 `using`），但文档和工具介绍里都没说 —— 第一次用必然失败一次（`CS0542` / `A using clause must precede...`）。v4 里 `content` 的含义**跟着 `typePath` 走**：指向类时是**成员**，指向命名空间时是**类的完整声明**。对应 §2、§10。

[^10]: **差异**：v3 里新建类型的壳是写死的 `public class {名}`，`[McpServerToolType]`、`static`、`partial` 都只能落盘后手工补 —— 而 MCP 工具类漏了 attribute 就**静默不注册**（没有编译错误）。v4 直接写你给的那段声明。同时 `memberName=""` 对**已存在**类型从"往类体里追加"改成"整类替换"。对应 §1、§8。

[^11]: **差异**：v3 匹配不上时不报错，而是当成"新增"照写 —— 结果同一个成员出现两份（`CS0111`），只在预检诊断里才看得出来。v4 直接报错，并在消息里给出"本类型里有个 X，是不是想写它"。对应 §7。

[^12]: **差异（修 bug）**：v3 的 `AddPartial` 把 `partial` 插在**访问修饰符之后**，于是 `public static class` 变成 `public partial static class`（`CS0267`）—— 每次给带 `static`/`sealed` 的类加成员都会踩。v4 插在**所有修饰符之后**。对应 §3。

[^13]: **差异**：v3 的求值缓存指纹是 `文件数 + 最新写入时间`，于是"只改了某个 `.cs` 的内容"也会让整个 MSBuild 求值作废 —— 但求值结果里跟 `.cs` 有关的**只有文件列表一项**，改内容不影响它。v4 的指纹只认"排序后的源文件路径集合"。对应 §4 的可优化点。

[^14]: **为什么这样是安全的**：读文件 + 绑定符号的那一层（`LoadedProject.Load`）本来就没有整份编译的缓存，每次都重读磁盘，所以内容变化一定看得见；只有**程序集引用**有缓存（跟源码正文无关）。所以"求值缓存沿用 + 重读文件"既省时间又不会给出旧信息。

[^15]: **新增（安全）**：v3 的落盘会跑 `dotnet format`，但文档没提它意味着什么。同类工具已经因此吃过 CVE（`roslyn-codelens-mcp` 的 `get_diagnostics` 无白名单加载并执行 analyzer 程序集，见《Csharp工具痛点》§7 之 3）。v4 至少把"这次加载了几个 analyzer"写进输出，让人能发现异常。

[^16]: **差异**：v3 的 `symbols` 是"两种模式"（`read=false` 列成员 / `read=true` 看结构），**列出来的信息量是固定的** —— 想看实现体得把 `path` 指到成员上；想看"谁在用它"则**根本没这个能力**（那个字母 `D` 管的是"只看带文档注释的"，那还是个筛选）。v4 把它拆成两层：前三个参数管**筛选**（列哪些），后三个布尔管**每条列出什么**（文档注释 / 被引用 / 实现）。原来的 `read` 被这三个开关收编 —— 旧 `read=true`（看结构、成员体隐藏）等价于三个开关全关；旧 `read=false` 的默认行为不变。

[^17]: **差异**：v3 没有改名能力；这里原本的设计是 `dryRun` + 自己写盘，等于在拟定流程之外开了**第二个写盘口子**。v4 把它收成"只往拟定里加一条"，写盘统一由 `confirm_draft` 负责 —— 一次落盘要么全成要么没动，也不会出现"改名的许可"和"改实现的许可"两张票。

[^18]: **差异**：v3 每次 `stage_draft` 都 `LoadedProject.Load` 一次（读盘 + 求值 + 建编译）。改成"加载一次、之后只在内存里换语法树"之后，拟定期间磁盘完全不动 —— 快，而且没有"读到一半被别人改了"的窗口。

[^19]: **差异**：v3 的 `stage_draft` 只做**语法**检查（`CodeEditor.EnsureMembersParse`），编译要等到 `confirm_draft` 预检 —— 于是错误是**攒出来的**，发现时已经不知道该退到哪一步。v4 每加一条就在内存里编译一次，并报**新增/消失的诊断**而不是绝对对错：串行拟定的中间态天然可能不完整，报绝对对错会一直吵。

[^20]: **差异**：v3 的 cookie 是随机 GUID，配一张"cookie → 状态"的表。v4 改成从内容算哈希：幂等、不占内存、不怕进程重启。代价是每次要重算（但拟定本来就要编译，顺带的事）。追踪 cookie 是唯一一处需要取舍的 —— 用它反查项目，要么把路径一起带在 cookie 里，要么留一张小表。

[^21]: **要求（语义比较）**：cookie 建在源码文本或语法树上都会误报 —— `List<int>` / 全名 / `using` 别名、`this.Foo()` / `Foo()`、注释与排版，全都是"语义没变、文本变了"。改成建在 **`IOperation`（操作树）**上：语法糖在这一层已经拆掉、引用的是符号，于是**语义不变就必然算出同一个 cookie**。反过来，`a + 0` / `for` vs `while` 这类**程序等价**归不到一起 —— 判定"两段代码是不是同一个程序"没有有限规则（一般不可判定），只能保守地误报，但不漏报。

[^22]: **要求（粒度比文件细）**：落盘前要算"磁盘现在 vs 快照时"的差异。v3 只有"文件被占用 / 有未解决冲突"这种粗判断，粒度要么整个文件、要么整个项目 —— 于是"别人改了同一个文件里的**另一个**类"也会把你拦下来。
>
> **实现落到了符号级**（比这里说的"类级"更细，也更好）：追踪基线本来就是「符号 → 语义 hash」的表，冲突检测只比**拟定涉及的那些符号**。所以"别人改了同一个文件里的另一个类、或者同一个类里的另一个成员"本来就不会被拦 —— 用不着先聚合成类再比。粒度更细、判断更准，这条**不需要**再往类级退。

[^23]: **要求**：引用列表只回答"**哪个类的哪个成员在用它**"（或者"类本身" —— 那是继承 / 实现），**不掺文件与行号**。位置是**另一个问题**：要位置就再查一次那个符号（`path='Ns.Type.Member(...)'` 会一并给出文件与行号）。两件事挤进一个列表，会让"谁依赖我"这个答案被一堆路径淹没。

[^24]: **差异**：v3 的 `type` 字母表里，`D` 是"只列带 XML 文档注释的"（那是个筛选）。v4 把"文档注释"挪去当信息开关（`documentation`），`D` 就空出来了 —— 回收给**委托**（`delegate` 在 Roslyn 里是 `INamedTypeSymbol` 且 `TypeKind.Delegate`，独立于 class / struct / interface 之外）。字母表照样是 `NCSITPFEMD`，但 `D` 的含义换了。

[^25]: **差异**：v3 的 `memberName` 要求"含参数表以消歧"，可**新成员根本没有参数表可写** —— 于是"加一个成员"这件事，只能写成一条已有成员的路径才能表达，语义上是拧的。v4 把路径的含义交给 `typePath` 指向什么：指向**类** = "改这个类的成员"（`memberName` 只是新成员的名字，跟已有重载撞名才需要参数表）；指向**命名空间** = "在这个命名空间下加一个类"（`memberName` 忽略，类的声明写在 `content` 里）。
