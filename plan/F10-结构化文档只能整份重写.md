# F10 · 结构化文档改一处，只能整份重写

| | |
|---|---|
| **状态** | 已解决（`Structured` 的 `read_structured` / `edit_structured`） |
| **涉及** | Structured |
| **相关** | 独立。与 F9 是同一类问题的两半：F9 是"有符号的代码"，这条是"没符号的配置/数据" |

## 背景

json / yaml / toml / ini / xml 这类文件里，AI 经常只改**一个值**：把一个开关打开、把一个版本号换掉、
给一个数组加一项。

## 现状

- 宿主能做的只有 **整份读、整份写**。要改一个值，就得把整份内容搬进上下文、改一处、再整份写回。
- **搬一趟就有一趟的损耗**：几百行的 yaml，上下文里全是与这次改动无关的行；
  写回时**格式还会变**——缩进、引号风格、注释位置、键的顺序，全凭序列化器的心情。
- 于是**diff 变成整份**：评审的时候看不出到底改了什么（改了一个值，diff 却是两百行）。
- 注释最惨：多数解析器读的时候丢掉注释，写回时注释就没了。
- 几种格式各有各的语法，AI 得记住四套。

## 期望

- **按位置改**：给一个路径（`$.logging.level`、`/config/logging/@level` 这种）和新值，
  只改那一处，**其余原样**（包括注释、缩进、键序）。
- **读**也能按路径读一段，不必整份进上下文。
- 一次调用可以给多条修改（`edits`），要么全成、要么全不动。
- 与 F1 一致：改已有的文件要凭据。
- 改坏了不行：**先看改动清单、确认了才落盘**。

## 验收

- 改一个值之后，diff **只有那一行**（缩进、引号、注释、键序都不变）。
- 文档里有注释时，改完之后注释**还在原位**。
- 路径写错时**报出来**，不是"改了个新地方"。

## 不包含

- 不做"重新格式化整个文档"——那正是这条痛点要避免的。
- 不做 schema 校验（json schema / xsd 之类的合规检查），那是另一件事。
- 不做结构化查询语言（jq 那套语法）——路径的写法要足够简单，能让 AI 一次写对。
- 不管**新建**一份结构化文档（新建没有"原样保留"可言）。
