# plan/ —— 痛点与提案

这里放两样东西：

- **痛点**（`F*.md`，本目录下）：按 GitHub feature request 的写法，一条一个文件。
  它回答"**为什么要做这个项目**"——现在缺什么、为什么现有手段不够。
- **提案**（`Csharp/`、`Resource/`、`Structured/`、`Workflow/`）：按项目分目录，一个闭环一篇。
  它回答"**打算怎么做**"——为什么这么设计、不打算做什么、代价是什么。

原本这些应该写成 GitHub Issue 与 RFC，但这个仓库现在是开发环境，所以落在本地。

## 痛点怎么算一条

**只写真正独立的那条。** 判据：

- ✅ **能独立讲清场景**："压缩包里的东西不解压就够不着" —— 一条。
- ✅ **同一个问题的衍生**也算得上一组，但要**写清它们同源**。
- ❌ **交叉组合不算**："改压缩包的时候不知道包被外部改过" —— 这不是独立痛点，
  是「F6 压缩包」与「F1 外部更改」撞在一起时的**具体设计**，落到那两篇提案的**设计**一节。
  没人会先想到这一层，所以它不配占一条。

一句话：痛点是**用户会碰到的事**，不是**两条设计拼起来的边界情形**。

## 提案怎么算一篇

**一个闭环一篇。** 判据：

- 这些工具**互相配合完成一件事** → 一篇（例如"改一份文件"是 凭据 → 改 → 落盘）。
- 只是**接口性质的解耦** → 分开写（例如压缩包单独一篇：它有自己的"看 vs 改""拟定 vs 落盘"）。
- 一个提案里可以有多组工具，但**闭环要是完整的**：用户拿着它能把一件事从头做到尾。

## 提案的固定小节

每篇提案按这十节写，顺序固定：

| 小节 | 写什么 |
|---|---|
| **摘要** | 两三句话：这是干什么的，解决哪条痛点 |
| **现状** | 市面上通用的 agent / 宿主有什么能力（不是"本仓库现在怎样"） |
| **动机** | 要做什么、为什么现状很难（引用 `F*`） |
| **非目标** | 明确**不打算**解决什么——防膨胀 |
| **设计** | 详情：这些工具怎么配合、什么流程、**预期返回什么、不返回什么** |
| **备选** | 择备方案：可用的、不想实现的、以及**试过走不通的** |
| **缺点** | 照实说，包括"这个设计会让人多一次调用"这类 |
| **待议** | 里面的魔数：缓存时间、容量上限、超时、批次…… |
| **影响** | 有了它，还能将就做什么；它会催生 / 挡掉什么 |
| **适用** | 什么情况下它就不管用了（例如宿主自己就长出了这个能力） |
