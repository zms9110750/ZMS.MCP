# F1 · 别人改了文件，AI 不知道

| | |
|---|---|
| **状态** | 已解决（`Resource` 的凭据两段式、`Csharp` 的拟定基线校验） |
| **涉及** | Resource、Csharp、Workflow |
| **相关** | F2（删了就没了）、F5（失败了却像成功）——同属"改动的可信度"这一组，但各自独立 |

## 背景

AI 读了一份文件、想好要改哪几处，等它把改动交回去的时候，**这份文件可能已经不是它读的那一份了**——
用户在自己编辑器里改了、另一次工具调用改了、`dotnet format` 跑过、`git checkout` 换过分支。

AI 看不到这些。它手里的"上下文里的那一份"是**过去的快照**，而它以为那是现在。

## 现状

- 宿主（编辑器）自带的能力里，`write_file` 是**整份覆盖**：AI 把"它记忆里的全文 + 一处改动"写回去，
  中途别人的改动就被**静默抹掉**。这是最常见的一种损坏，而且**不回滚**。
- 文件系统本身不提供"我上次看到的版本"这个概念；`mtime` 有，但没人拿着比对。
- 市面上的 MCP 文件工具基本都是"路径进、内容出"，没有一个是**两段式**的。
- 本仓库原有的 `Csharp` 侧有一半：拟定的基线 hash 校验（`stage_draft` 记基线，`confirm` 落盘前比对）。
  但那只是**一个项目内的一条链路**；`Resource` 的读写、`Workflow` 的落盘当时都没有。

## 期望

改动**已有的**东西时，调用方必须能证明"我知道我要改的是什么"：

- 读过之后拿到一个**不透明的短标识**，改的时候带回来；
- 对不上就**不执行**，并把"现在是什么样"报出来（而不是替谁猜）；
- 缺标识、标识过期，都算**两段式的正常第一段**，不算失败。

## 验收

- 一份文件被外部改动后，带旧标识的改动请求**被拒绝**，且返回里能看出"这期间它被改过"。
- 只读了元数据（没读全文）就能拿到的标识，与读过全文的标识**能互相校验**（前者不该因为缺内容段而被拒）。
- 检测到"文件不存在"这一档也能表达：新建走它，覆盖已有文件不认它。

## 不包含

- **不做**"改了之后自动合并"——发现冲突就交回给人，AI 不替人裁。
- **不管**"压缩包被外部改动"这类组合场景：那是 F6 与 F1 的交叉，落进各提案的**设计**一节，
  不单独立一条痛点（没人会先想到"改包要先看包变没变"）。
- 不做文件系统的实时监听 / 订阅。
