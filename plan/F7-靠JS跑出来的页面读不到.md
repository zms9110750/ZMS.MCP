# F7 · 靠 JS 跑出来的页面，取回来是空壳

| | |
|---|---|
| **状态** | 已解决（`Resource` 的 `browse`，用系统自带的 Edge/Chrome 渲染） |
| **涉及** | Resource |
| **相关** | 独立；与 F8 同属"访问网页的障碍"，但成因与对策都不同 |

## 背景

现代网页的正文往往**不是**写在 HTML 里的——它是页面加载后由 JS 填进去的：
文档站、控制台、几乎所有 SPA、以及大量"看板"类页面。

## 现状

- 直接取（HTTP GET）拿回的是**骨架**：有 `<title>`、有脚本标签、正文区是空的。
  AI 会**照着这个空壳编**——它以为那就是页面内容，然后基于空白往下推理。这比取不到更糟。
- 宿主虽然自己有浏览器能力，但**服务端不知道**：从 MCP 这一侧取，就是纯 HTTP。
- 有些页面还要先滚动、先点一下、或者等某个接口回来才出现内容——纯 GET 永远等不到。

## 期望

- 有一个"**把页面打开、等它跑完、再把内容给我**"的动作，而不是只发一次 GET。
- 等不到超时了**如实说**（说清等了多久、等的是什么），不要返回半加载的骨架当正文。
- 结果**不进缓存**（F3 那条缓存是给"取回来的字节"用的；渲染结果是一次性的现场）。
- 渲染要能用**本机已有的浏览器内核**，不额外下载一个几百 MB 的运行时——这是给别人用的项目。

## 验收

- 对一个正文靠 JS 注入的页面取内容，拿到的是渲染后的文本，不是空壳。
- 超时被明确报出来，且明说"等到的是什么状态"。
- 首次使用时如果本机没有可用浏览器，报出的错误**说清装什么**、以及怎么改配置。

## 不包含

- 不做自动化操作（点击、填表、登录流程）——只做"打开、等、取内容"。
- 不做"替我过验证"——那是 F8。
- 不做截图（图像不进上下文，对 AI 没用）。
- 不保证渲染与真人看到的一致：这是**尽力而为**，不是浏览器兼容性项目。
