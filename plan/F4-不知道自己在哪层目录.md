# F4 · AI 不知道自己碰的是哪一层目录

| | |
|---|---|
| **状态** | 已解决（`Global.cs` 的工作空间边界 + 调用过滤器） |
| **涉及** | 全部 MCP 项目（共享层） |

## 背景

AI 拿到的路径是**字符串**：`path`、`csprojPath`、`targetPath`。它按相对路径解析、按当前目录解析，
而**当前目录是宿主启动服务时给的那个**——AI 看不见这个事实。

于是会出现：AI 以为在 A 项目里改文件，实际落到了别处；或者用户说的是"那个项目"，AI 解析成了上一个项目的路径。

## 现状

- 相对路径的基准（进程当前目录）**对调用方不可见**：`instructions` 里不写、工具返回里也不提。
- 越界没有反馈：写成功就是成功，落点错了也照样"成功"。
- 每个工具各写各的路径处理，**同一条规则在四个项目里各实现一遍**（改一处漏三处）。
- 与之相关的一个后果：**同一会话里几个 MCP 服务的工作区可能不同**，而 AI 默认它们一样。

## 期望

- 服务启动时就把**边界是什么**告诉调用方（写进 `instructions`，一上来就能看到）。
- 每次调用涉及路径的参数**在工具执行之前**就检查；越界时**拒绝**，并在拒绝里说清三件事：
  你给的是哪个路径、边界是哪些、想越界该怎么办。
- 边界可由环境变量指定（多个目录），取不到就退回进程当前目录。
- 这条规则**只实现一次**，四个项目共用。

## 验收

- 传一个边界外的路径，工具**没有被执行**（不是执行完才报错），返回里带上给出的路径、边界、以及怎么放宽。
- 容器内的路径（压缩包里的路径、FTP 会话里的路径）**不被误判**成越界的本地路径。
- 符号路径（`Ns.Type.Member` 这种没有分隔符也没有盘符的值）**不被误判**成文件路径。

## 不包含

- **这不是安全边界**。服务是独立进程、用启动者的权限跑，宿主自己就有命令行——真想越狱谁也拦不住。
  它要解决的是"让调用方知道自己碰的是哪儿"，不是"防止恶意调用"。
- 不实现 MCP 的 roots 协议（协议本身也不强制）。
- 不做路径的权限检查（该不该写由操作系统决定）。
