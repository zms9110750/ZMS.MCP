# F3 · 同一个地址读两次，网络跑两遍

| | |
|---|---|
| **状态** | 已解决（`Resource` 的 `fetch` + `cache`） |
| **涉及** | Resource |

## 背景

AI 干活时会反复取同一份东西：查一个 API 的文档、看一个包的说明、读一个网页的表格。
**它不记得刚才取过**——上下文被压缩、换了会话、或者它只是想确认一下。

## 现状

- 宿主的取网页能力：**取一次、进一次上下文**。同一地址第二次取，网络照跑，内容照进上下文。
- 于是同一页内容可能在一次会话里进上下文三遍：横向对比时取一遍，确认时取一遍，写总结时又取一遍。
- 更大的那份代价在**长内容**：一个几百 KB 的 JSON/HTML 取进来，往往只有一小段有用，
  但整份都进了上下文——**token 花在了用不上的部分**。
- 宿主也没有"取下来放旁边、只给我看一段"的做法：取就是取，看就是全看。

## 期望

- 取回来的东西可以**只给一个短标识**进上下文，正文留在服务这边；
- 想看哪一段，**按标识再取那一段**（而不是整份重进上下文）；
- 标识跨调用有效，**跨会话**也能用（同一天里重启了客户端还在）；
- 返回里**说清**这次是"刚取的"还是"从缓存拿的"——不能让人以为刚取过。

## 验收

- 取过的内容，第二次**可以从缓存里拿**（`cache`）而不必重跑网络；
  但**取的时候不会自动命中**——想省这一趟，得显式去取（这条与设计对得上，别指望"取一次就自动不跑"）。
- 只取内容的一段（例如第 3 个段落）时，进上下文的就是那一段，不是整份。
- 标识在进程重启后仍然查得到（缓存落了盘）。

## 不包含

- **不是为了"给对端省流量"**——限流一类属于礼貌，不是这条痛点的诉求。
- 不做条件请求（`ETag` / `If-Modified-Since`）那套缓存协商：这条只说"取过的别再取"。
- 不做"把网页转成 markdown 提取正文"——那是解析，另一件事。
