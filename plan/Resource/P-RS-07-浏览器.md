# P-RS-07 · 浏览器（`browse`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Resource` |
| **痛点** | [F7](../F7-靠JS跑出来的页面读不到.md)、[F8](../F8-人机验证过不去.md) |
| **状态** | 部分实现（渲染已做；"人过完怎么继续"仍待议） |
| **工具** | `browse` |

## 摘要

把页面**真的打开**、等它跑完 JS、再把内容取回来；以及在被拦下时**如实说拦住了**、
需要人的时候起一个**用户能看见**的窗口。它解决"取回来是空壳"与"静默被拦"这两件事。

## 现状

- 直接取（HTTP GET）拿回的是**骨架**：正文由 JS 填，纯 GET 永远等不到。
  AI 会照着空壳编——**这比取不到更糟**（[F7](../F7-靠JS跑出来的页面读不到.md)）。
- 宿主自己有浏览器能力，但**服务这一侧不知道**：从 MCP 取，就是纯 HTTP。
- 被拦时更糟：挑战页 HTTP 200、有 HTML、有标题，**看起来是一份正常响应**。
  AI 把"请稍候，正在验证"当成正文分析（[F8](../F8-人机验证过不去.md)）。
- 人机验证的设计意图就是"证明对面是人"——**不存在"正确地通过它"**。
- 宿主的浏览器与服务侧的浏览器**不是一个**：用户在宿主里过了验证，服务这边的会话并没通过。

## 动机

- **要拿到渲染后的内容**（[F7](../F7-靠JS跑出来的页面读不到.md)）；
- **要在被拦时说实话**，并且**在需要人时把人请进来**（[F8](../F8-人机验证过不去.md)），
  而不是绕过去。

## 非目标

- **不做**打码平台、破解挑战参数、stealth 反指纹、代理池轮换——那是**对抗对方明确表达的意图**。
- **不做**自动化操作（点击、填表、走登录流程）：只做"打开、等、取内容"。
- **不做**截图（图像不进上下文，对 AI 没用）。
- **不承诺**任何站点都能过：有的站点就是不允许非人类访问，那就如实报"过不去"。
- **不做**浏览器兼容性项目：渲染结果是**尽力而为**。

## 设计

### 一个工具，两个动作

| `action` | 行为 |
|---|---|
| `open`（默认） | 打开就返回 |
| `wait` | 等页面稳定再返回（可给等待条件，如网络空闲 / 固定时长） |

超时控制：默认 30 秒；超时**如实报**（等了多久、等的是什么、当时页面是什么状态），
**不返回半加载的骨架当正文**。

### 用本机已有的浏览器内核

复用**系统自带的 Edge / Chrome**（不下载一个几百 MB 的运行时）。这是给别人用的项目，
不能要求每个人先装一个浏览器引擎。

### 人机验证：可见窗口 + 会话留在服务这一侧

**一个技术硬约束**（选错了会白做）：

> 验证的产物（会话 / cookie）**必须落在"要用它的那个进程"手里**。

所以**不能**让用户去系统浏览器里过验证——那样 cookie 在别人那儿，抓取还是失败。
正确做法是**服务自己起一个可见的浏览器**，宿主只负责把它呈现出来。

流程（**待议**，目前只做到"能起可见窗口"）：

1. 识别到拦截 → **明确报"这是拦截，不是内容"**；
2. 请求用户介入（这一步怎么发起见待议）；
3. 用户过完 → **同一次工具调用继续**（不要求用户重发）。

### 预期返回什么 / 不返回什么

- **返回**：渲染后的页面内容；超时的说明；被拦时**明确指出这是拦截**。
- **不返回**：渲染结果**不进缓存**（它是一次性的现场）；
- **不返回**：挑战页的内容当正文；不返回截图。

## 备选

- **可用的**：让宿主自己去渲染（"你在本地开一个浏览器，把 HTML 喂给我"）。
  **不想实现**——宿主的浏览器与服务侧的会话不是一回事（见上面那条硬约束）。
- **可用的**：**下载**一个浏览器内核（Playwright 自带的那套）。**不想实现**——
  几百 MB 的下载对"给别人用"这件事太重；复用系统浏览器是更小的代价。
- **走不通的**：用 `WebView2` / 系统 WebView 控件做渲染。
  它需要 UI 线程与消息循环，而这是一个 stdio 服务，没有界面线程。
- **走不通的**：纯 HTTP + 自己解析 JS。**这是不可能的**——现代的页面是运行时生成的，
  静态解析拿不到内容。

## 缺点

- **依赖本机有 Edge / Chrome**：没有就报错（报错会说清装什么）。这是"不下载运行时"换来的代价。
- **起浏览器很贵**：进程启动、页面加载、等 JS——比一次 HTTP GET 慢一个数量级。
  所以它只该用在"确实需要渲染"的地方。
- **渲染结果不进缓存**：同一个页面反复渲染就反复付这个代价。
- **人机验证那半没做完**：现在能起可见窗口，但"用户过完之后怎么让这次调用继续"没定（见待议）。
- **只在 Windows 上验证过**。

## 待议

- **默认超时（30 秒）**、**等待条件**支持哪些（`networkidle` / 固定时长 / 某个选择器）。
- **"过完怎么继续"**：是让这次调用**阻塞等人**（可能几分钟），还是中断并让调用方带一个"我过完了"的令牌回来？
  后者需要一次额外的调用，前者需要很长的超时——两条路都别扭，这条必须定下来。
- **窗口归属**：服务起的浏览器窗口怎么让用户注意到（任务栏？宿主展示？）。
- **浏览器依赖探测**：找不到 Edge/Chrome 时给什么指引（版本要求？安装链接？）。
- **要不要支持"带 Cookie 复用会话"**（这次渲染的登录态，下次还用）——这会牵扯凭据管理。
- **渲染结果的交付量上限**（大页面转成文本可能几十 KB）。

## 影响

有了它，AI 可以：

- **读现代网页**（文档站、控制台、看板），这是纯 GET 做不到的。
- **不再把"请稍候，正在验证"当正文分析**——被拦会明说。
- **将就着做**"页面快照"：渲染一次拿到文本，够判断页面在讲什么。

它会催生什么：**"人参与的调用"这个机制**（[F8](../F8-人机验证过不去.md) 那半）——
一旦"请求人介入、人做完、调用继续"这条链打通，其他"AI 不该独自做"的动作也能复用
（例如 [P-RS-03](P-RS-03-删除与移动.md) 里"进不了回收站"的交回用户）。
它会挡掉什么：不需要再考虑"给 agent 一整套浏览器自动化脚本"——那既是权限问题也是维护问题。

## 适用

**以下情况它就不管用了：**

- **宿主自己会渲染**：如果编辑器侧能"打开页面并把 DOM 交给我"，这一层是重复的。
- **本机没有 Edge/Chrome**：直接报错，帮不上忙。
- **整站不允许非人类访问**：如实说"过不去"，这是设计的一部分。
- **需要登录才能看到的页面**：不做认证与 Cookie 管理。
- **要抓的是接口而不是页面**：那走 [P-RS-05](P-RS-05-网络与缓存.md) 的 `fetch` 更合适——
  渲染是最后手段，不是默认。
