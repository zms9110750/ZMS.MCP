# P-RS-04 · 压缩包（`track_archive` / `confirm` + 包内读写）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Resource` |
| **痛点** | [F6](../F6-压缩包里的东西够不着.md)、[F1](../F1-别人改了文件.md)、[F2](../F2-删了就没了.md) |
| **状态** | 已实现 |
| **工具** | `track_archive`、`confirm`（包内的读 / 列 / 写 / 删挂在 `read` / `list` / `copy` / `delete` 上） |

## 摘要

**看**压缩包不解压（列条目、读某一条），**改**压缩包先攒成一份拟定、确认后一次性重写整包。
它是 `Resource` 里唯一一个"另一类对象"的独立闭环：读写都挂在既有工具上，但"改"这件事需要它自己的两段式。

## 现状

- 要看包里一个文件，只能**整份解压**：几十 MB 的包展开占磁盘，看一行就走，剩下全留着当噪音。
- 看包里的目录结构也得先解开——而这件事纯读元数据就够了。
- 往包里放一个文件 / 删一个文件：解压 → 改 → 重新打包，**中途失败得到一个半成品**。
- 不同格式各有各的命令行（zip 用 `Expand/Compress-Archive`，tar/tgz 用 `tar`），手段不统一；
  而 nupkg 之类的"其实是 zip 的"格式还要知道它的真身。

## 动机

把压缩包当成**容器**而不是"一堆文件"（[F6](../F6-压缩包里的东西够不着.md)）：

- 读：按需取一条，不落盘；
- 改：像 `Csharp` 的拟定那样，**先说清改什么、确认了才重写整包**——
  因为多数格式**天生不支持"就地改一个条目"**，改一条就得重写整包，那么"攒起来一次做"才是对的。

## 非目标

- **不做**包内文件的**部分更新**（改一个字节就地写回）：多数格式不支持，硬做会让整个包的结构失效。
- **不做**加密压缩包（带密码的 zip / 7z）的读写。
- **不做**增量打包（只重写变化的部分）——现在是整包重写，包大时这是**代价**（见缺点）。
- **不做**跨包移动（从 A 包搬到 B 包）——先取出来、再放进另一个，两步已有。
- **不做**自建压缩格式 / 自研解析。

## 设计

### 两个动作，四种格式

```
track_archive(path)                     → 追踪一个包（不带 cookie 开始，带 cookie 解除）
   ↓ cookie
copy / move / delete（target = 那个包）  → 只**攒一条拟定**，不动磁盘
   ↓
confirm(cookie)                         → 预检：落盘后包里会变成什么样
confirm(cookie, applyCookie)            → 真的重写整包
```

- **看包不需要追踪**：`read` / `list` 直接读磁盘上那个包，随时可用。
- **改包必须先追踪**：往拟定态包里做的改动先攒着。
- **格式**：zip / 7z / tar.gz / tar+zstd 四种。zip 与 7z 走归档库，tar 系列走流式读；
  读法按格式分流（7z 走归档，其余走流式）。

### 落盘怎么做

1. **重读比对**：拟定期间包被人动过（大小或修改时间对不上）就**拒绝落盘**（[F1](../F1-别人改了文件.md)）；
2. 在内存里把整包重放一遍（保留的条目 + 新增的 − 删除的）；
3. **先写临时文件、再原子替换**——中途失败原包不动。

### 规模上限

| 合计大小 | 行为 |
|---|---|
| 正常（< 50 MB） | 直接落盘 |
| > 50 MB | **先问宿主**（要确认） |
| > 1 GB | **不给打**，交用户手动处理 |

### 预期返回什么 / 不返回什么

- **返回**：包内条目清单（路径 / 大小 / 时间 / **每条自己的凭据**）；
  拟定态下返回"这一类里现在攒了几条"；预检返回**落盘后包里的完整条目清单**。
- **返回**：落盘后的包大小与条目数、以及**新的凭据**（追踪还在，cookie 不变）。
- **不返回**：包内所有条目的内容（列结构时不读内容）。
- **不返回**：猜测——格式认不出、条目不存在，都明确报错。

## 备选

- **可用的**：解压到临时目录去改。**不想实现**——它把"看一条"变成"展开整包"，
  正是这条痛点。而且中途失败留下半成品。
- **可用的**：只做读、不做写（"压缩包当只读容器"）。**不想实现**——往包里放一个文件是真实需求
  （发布产物、补一个文件），不做的代价是调用方回退到"解压 → 改 → 重打"。
- **走不通的**：`WriterFactory.Open(stream, type, options)` 那种"边写边加条目"的旧写法——
  现在的库版本里签名变了（要走 `OpenWriter` + `IWriterOptions`）。
- **走不通的**：用某个格式的**增量写**（只追加、不重写）。zip 可以追加条目但**不能改已有条目**，
  一旦有"删一个条目"的需求就不成立，所以干脆统一按整包重写。

## 缺点

- **整包重写**：改一个条目也要把整包读进内存、重写一遍。**包大时这是主要代价**（1 GB 的包会直接拒绝）。
- **必须先追踪才能改**：多一次调用，且"追踪状态"是一个要维护的东西（进程重启后靠拟定表拿回来）。
- **看包不受凭据保护**：`read` / `list` 打进包里不需要追踪——这是有意的（看是安全的），
  但也就意味着"看"到的东西可能下一秒就变了。
- **ztsd 只有一半**：能读（流式读支持），能写（用库自带的能力把 tar 包一层）；
  但这类边角格式的支持面取决于第三方库，不是我们能控制的。
- **只读元数据拿不到大小时**：某些格式（7z）读出来的大小可能不准，那就只作展示用。

## 待议

- **> 50 MB 要问宿主**、**> 1 GB 不给打**：这两个数是拍的。
- **拟定能攒多久 / 包能追踪多久**：现在没有过期，进程重启后还在。
- **预检要不要给"大小变化"的预估**（现在给的是落盘后的条目清单，不给"会比原来大多少"）。
- **格式认不出来时**：现在是报错。要不要支持"按扩展名硬试"。
- **"包里条目自己的凭据"用不用内容段**：现在用元数据段（路径 + 大小 + 时间），
  因为改包是"整份重写"，不需要内容级的比对。
- **能不能给"跨包移动"**（现在是两步）。

## 影响

有了它，AI 可以：

- **在几十 MB 的包里看一个文件**，不展开、不留垃圾。
- **安全地改包**：改之前能看到"落盘后包里长什么样"，改砸了（包被外部动过）会被拒绝。
- **将就着做**"包内容审查"：列条目 + 按需读几条，够判断一个包是不是该删。

它会催生什么：**发布产物相关的流程**（往包里补一个文件、把 nupkg 打开核对内容）。
它与 [P-CS-02](../Csharp/P-CS-02-拟定两段式.md) 是**同一个思路的两次实现**：
那边"内存里投影编译"，这边"内存里重放整包"——两边的"拟定 + 确认"应当保持同一套词汇与错误形态。
它会挡掉什么：不需要再考虑"给 agent 一条打包命令"（`tar` / `Compress-Archive`）——
那正是"解压 → 改 → 重打"那条路的入口。

## 适用

**以下情况它就不管用了：**

- **宿主的文件管理器就是压缩包工具**：如果宿主能"打开 zip 里的一个文件"并把这件事开放给 agent，
  这一层是重复的。
- **包大到内存放不下**：现在是整包重放，几百 MB 以上就该交给外部工具。
- **加密包**：不支持，直接报错。
- **托管平台上的包**（远端 zip）：远端只能读与搬运，**不能改**（FTP 那边一切写操作都受限）。
