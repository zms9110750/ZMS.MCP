# P-RS-02 · 本地写（`write` / `replace`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Resource` |
| **痛点** | [F1](../F1-别人改了文件.md)、[F11](../F11-读大文件里的几行.md)（编码那半） |
| **状态** | 已实现 |
| **工具** | `write`、`replace` |

## 摘要

**新建**一份文件，或者**覆写**一份已有文件——两者都要先满足"我知道我要改的是什么"。
改一份文件里的**几处**内容用 `replace`：给正则与替换内容，只动命中的地方，其余原样。

## 现状

宿主的写文件是**一次调用、整份覆盖、不问不预览**：

- 覆写时，AI 把"它记忆里的全文 + 一处改动"写回去，**中途别人的改动被静默抹掉**（[F1](../F1-别人改了文件.md)）。
- 改一处也要**整份写**：几百行的文件进上下文、改一行、整份写回。
- 写回去的**编码是宿主决定的**（通常是 UTF-8），于是一份 GBK 的老文件被"改一个错别字"之后，
  中文全成了问号。
- 替换是**纯文本**的：想"只改第 2 个匹配"或者"用捕获组换一种写法"，得自己拼。

## 动机

把"改动已有内容"这件事**从一次调用变成两段**：先说清改什么、给一个凭据，第二次带着凭据才真写。
并且让**写回用读进来时的那份编码**（[F11](../F11-读大文件里的几行.md) 的写回一半）。

## 非目标

- **不做**事务/回滚（"写失败了帮我恢复"）。写文件本身是原子的（先写临时文件再替换），
  但不提供跨文件的撤销。
- **不做**行级补丁格式（unified diff）的输入——那是另一个接口风格，且要求调用方会写 diff。
- **不做**"批量替换整个目录"。
- **不做**新文件的权限/属主设置（用默认的）。

## 设计

### 两个工具，分工按"改什么"划

| 工具 | 干什么 | 覆写已有内容时 |
|---|---|---|
| `write` | **新建**或**整份覆写** | **要 `cookie`** |
| `replace` | 改文件里的**一处或几处** | **要 `cookie`** |

两者都遵守：**目标不存在 → 不要凭据**（没有"别人"可覆盖）；**目标已有内容 → 必须给凭据**，
对不上就不写、并把"现在是什么样"报出来。

### `replace` 的两个要求

- **必须先捕获**：匹配用的是**正则**，替换内容里可以引用捕获到的片段（`$1` / `${name}`）。
  这样"把 `v(\d+)` 换成 `version-$1`"是一句话的事。
- **命中多处怎么办**：要明说。默认要求收紧表达式；想一次改多处就给多条 `edits`，各自独立报错。

### 预期返回什么 / 不返回什么

- **返回**：写了哪个文件、**下一个凭据**（改完的这份的），以及"这批改动是新建 / 覆写 / 替换了几处"。
- **返回**：凭据对不上时，**现状**（多大、什么时候改的）与"它的凭据是什么"——让调用方知道下一步该 `read` 一次。
- **不返回**：写完之后文件的全文（要看就 `read`——那是另一个工具的活）。
- **不返回**："成功"两个字——要说清是哪种成功。

## 备选

- **可用的**：只做整份写，不做 `replace`。**不想实现**——"改一处要整份搬"正是这条痛点的一半。
- **可用的**：`replace` 只做**唯一命中**（多命中就报错）。这是现在的默认行为，但同时给了 `edits`
  让"确实要改多处"有出路。
- **走不通的**：把 `write` 与 `replace` 合成一个工具（按"有没有给正则"分态）。
  **不想实现**——`write` 是破坏性（整份替换），`replace` 是修改性的，两者的注解不一样；
  合成一个之后 MCP 的注解只能按最坏情况给。
- **走不通的**：`replace` 用**逐字节偏移**定位。偏移在文件被改一下就全错位了；
  而文本匹配 + 捕获至少说的是"要改的那段长什么样"。

## 缺点

- **`replace` 的"命中多处"很烦**：同一段文本在多处出现时，调用方得自己收紧正则——
  而它**看不到有几处**（`read` 的 `regex` 能看到，但那是另一个工具）。
- **正则是个门槛**：`oldString` 是正则意味着**特殊字符要转义**（想替换 `a.b` 得写 `a\.b`），
  这是最容易出错的地方。
- **凭据对不上时不给"帮我自动合并"**：只报现状。调用方必须自己 `read` 一次再改。
- **编码只能沿用**：想要"把这份文件转成 UTF-8"做不到（那是转换，不是写）。
- **整份覆写仍然要求调用方持有全文**：`write` 不是"边改边写"，它要的是完整的最终内容。

## 待议

- **`replace` 要不要默认允许多命中**（现在是要求收紧）。
- **`edits` 的上限**：一次最多给几条。
- **新文件的默认编码**（现在是 UTF-8 无 BOM）——要不要认 `.editorconfig` 的 `charset`
  （`Csharp` 那边认了，这里没有）。
- **`write` 能不能"追加"**：现在只有新建与覆写。追加是常见需求，但它不属于"整份覆写"，
  也不属于"替换"——要不要单开一个动作。
- **凭据对不上时，要不要顺带把"差异"给出来**（哪几行变了），而不只是给现状的元信息。

## 影响

有了它，AI 可以：

- **改一处而不毁掉整份**（无论是被别人改的部分，还是格式与编码）。
- **在两段式里做改动**——这是 `Resource` 侧与 `Csharp` 的拟定**对齐口径**的地方：
  两边都是"先说清、再落盘"，只是 Csharp 那边多一层"能编译"的预检。
- **将就着做**"安全的批量替换"：`edits` 一次给几条，各自报错。

它会催生什么：**压缩包内的改写**（[P-RS-04](P-RS-04-压缩包.md)）——包内条目也是"改已有内容"，
用的是同一套凭据与两段式思路，只是把"写哪里"换成了"包里的哪个条目"。
它会挡掉什么：不需要再考虑"让 agent 用命令行改文件"——那正是抹掉别人改动的主要途径。

## 适用

**以下情况它就不管用了：**

- **宿主自己做了并发检测**：如果写文件时宿主能检测"你读到的那版还在不在"，这一层就重复了。
- **要改的是结构化文件里的一处值**：`write` / `replace` 是**文本层**的，
  改 json/yaml 里一个值应该走 `Structured`（那边能保住缩进与注释，与 [F10](../F10-结构化文档只能整份重写.md) 同一件事）。
- **文件大到整份持不动**：覆写要求调用方手里有完整内容——几百 MB 的文件它做不了。
