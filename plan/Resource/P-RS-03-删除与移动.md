# P-RS-03 · 删除、移动与复制（`delete` / `move` / `copy`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Resource` |
| **痛点** | [F2](../改动的可信度.md)、[F1](../改动的可信度.md) |
| **状态** | 已实现 |
| **工具** | `delete`、`move`、`copy` |

## 摘要

删（走回收站，进不去就不删）、移（跨卷/跨存储时按"拷贝 + 删"两步，先落定目标再删源）、
复制（含往 FTP 上传、从 FTP 下载）。三者都是"改到已有内容"这一类，因此都要凭据、都要说清影响。

## 现状

- **删除是硬删**：命令行里 `Remove-Item -Force` 一句就没了，**不可恢复**。
  想走回收站要手写一段很长的 API 调用——**长、易忘，而忘了就不可逆**（[F2](../改动的可信度.md)）。
- **移动是同名覆盖**：把文件移到已有同名文件的目录，**直接覆盖、不问**。
- **跨设备移动不是移动**："移过去"实际上是"拷过去 + 删源"，中途失败会得到两边的半成品，
  而调用方往往以为它是一次原子动作。
- **复制到已有目录会静默混合**：目录里的文件被覆盖了一半，调用方不知道哪几个被换了。
- 往 FTP 上传/下载只能靠命令行拼 `FtpWebRequest`。

## 动机

- 让**删除可恢复**（回收站），并且在恢复不了时不替用户冒险；
- 让**会覆盖别人的动作**（移动、复制到已有内容）在动手前把影响摆清楚（[F1](../改动的可信度.md)）。

## 非目标

- **不做**"撤销"：删完之后没有再"恢复"的工具，回收站就是恢复手段。
- **不做**目录同步 / 镜像（"把这个目录变成那个目录的样子"）——那是另一类工具，且危险。
- **不做**批量删除（"把这些文件都删了"）这种便利动作：一次一个，或者逐个来。
- **不做**回收站的清理与管理。

## 设计

### `delete`：能不能进回收站，决定做不做

| 情形 | 行为 |
|---|---|
| 能进回收站 | 删入回收站，**告诉用户去哪找回来** |
| **进不去**（过大、网络盘、可移动盘、只读卷） | **不执行**，报出来交用户手动处理 |
| **远端（FTP）** | **不执行**（那里没有回收站） |
| 没给凭据 / 凭据对不上 | 不执行，报现状 |

「进不去回收站就不删」这条是**刻意的**：这是唯一不可逆的操作，工具不替用户承担这个风险。

### `move`：三种情形，凭据要求不同

| 情形 | 凭据 | 为什么 |
|---|---|---|
| 同一个容器、同一卷 | 不要 | 移回来就行，可逆 |
| **跨容器或跨卷** | 源要凭据 | 它**实际上是拷贝 + 删源**（不可逆的那一半在这） |
| 目标已有内容 | 目标也要凭据 | 会覆盖 |

跨容器/跨卷时**先落定目标、再删源**，中途失败**源不删**，并把"两边现在各是什么状态"报出来。

### 会覆盖时的两档预算

目标处有**冲突**（会合并的目录、会被替换的文件）时：

| 冲突数 | 行为 |
|---|---|
| ≤ 15 个 | **逐个列出来**，各给凭据，让调用方带回来 |
| > 15 个 | 说清有多少个，**要求用户来处理**（工具拿不到这种规模的授权） |
| > 50 个 | 直接拒绝（量级说明这不是一次"移动"，是被误用的同步） |

### 预期返回什么 / 不返回什么

- **返回**：删了/移了/复制了哪些路径；删除时**回收站的方向**（去哪找回来）；
  冲突时的**逐个清单 + 各自凭据**；跨容器失败时的**两边状态**。
- **不返回**：目录内容的全文；不返回"成功"两个字。
- **不返回**：目标处被覆盖的内容（没了就是没了——这也正是为什么要先要凭据）。

## 备选

- **可用的**：软删除到工具自己的目录（"回收站放在服务里"）。**不想实现**——
  用户的系统回收站才是他能自己找回来的地方；服务自己的目录还得再做一个管理界面。
- **可用的**：不管回收站，只做两段式确认（"确认了才删"）。**不想实现**——确认解决的是"想清楚了吗"，
  回收站解决的是"想错了怎么办"。两件事都要。
- **走不通的**：把 `move` 做成"同卷才允许"。**不想实现**——跨卷移动是最常见的需求之一，
  正确的做法是**如实说清它是拷贝 + 删**，而不是拒绝。
- **走不通的**：用一条"批量操作"工具处理大冲突（一次要几十个凭据）。
  实测判断是"这个规模不该由工具授权"，于是 >15 就交回用户。

## 缺点

- **冲突一多就交回用户**：15~50 个冲突之间，工具能列出清单但做不了事，得用户动手——
  这在"搬一个目录"时很容易撞上。
- **跨卷移动不是原子的**：先落定目标再删源，中途失败会**两边都留着**（源没删、目标写了）。
  返回里说清了状态，但调用方得自己收拾。
- **`copy` 与 `move` 的差别只在一句"删不删源"**，却要两套参数（`cookie` / `toCookie`），
  学起来有重复感。
- **回收站的可见性依赖平台**：Windows 上有；Linux 上"回收站"是桌面环境的概念，
  服务进程看到的可能就不是同一个——这块只在 Windows 上验证过。

## 待议

- **冲突分档的门槛**：≤15 / >15 / >50 这三个数是拍的，没有依据。
- **跨卷移动的"部分成功"要不要更强的报告**（现在给两边状态，但不给"下一步建议"）。
- **删除目录时凭据要覆盖到什么**：现在是"读整棵树"那份凭据。目录很大时，读整棵树的代价不低。
- **`copy` 往 FTP 上传要不要限速**（大文件上传期间的进度/超时）。
- **能不能给"移动一个目录"更省事的确认**（现在按冲突文件逐个要凭据，几十个文件就是几十个凭据）。

## 影响

有了它，AI 可以：

- **放心删**（能找回来），以及**在找不回来时被挡住**（而不是冒险）。
- **搬东西之前先知道会覆盖什么**。
- **将就着做**"清理"：删除 + 回收站能承担"我不再需要它了"这类判断。

它会催生什么：**压缩包内的删除**（[P-RS-04](P-RS-04-压缩包.md)）——包内删除同样是删除，
走同一套"要凭据 + 走拟定"的纪律。
它会挡掉什么：不需要再考虑"给 agent 一条通用的删除命令"——那正是硬删的来源。

## 适用

**以下情况它就不管用了：**

- **宿主自己做了删除保护**（回收站 / 软删除 / 版本历史），这层的增量就只剩"凭据"那半。
- **要删的东西大到回收站装不下**：那正是"不执行"的分支——它就只能报错，帮不上忙。
- **远端存储**：FTP 上一切删除都被拒绝（设计如此），所以"清理远端目录"这件事它做不了。
- **平台不是 Windows**：回收站这条路只在 Windows 上验证过。
