# F8 · 需要人过的验证，AI 过不去

| | |
|---|---|
| **状态** | 部分解决（`Resource` 的 `browse` 能起可见浏览器；"人过完怎么继续"仍未定，属**待议**） |
| **涉及** | Resource |
| **相关** | 独立；与 F7 都发生在"访问网页"这条路上，但一个要等待、一个要人 |

## 背景

有些站点在给你内容之前会拦一道：Cloudflare 的检查、滑块、点一个"我不是机器人"。
**这道关卡本来就是设计给人过的**，而 AI 不是人。

## 现状

- 硬闯没有正路：绕过去属于对抗，不该做。
- **更糟的是"静默被拦"**：拦下来返回的那页（挑战页 / 验证页）看起来**是一份正常响应**，
  HTTP 状态 200、有 HTML、有标题。AI 把它当正文读，然后基于一页"请稍候，正在验证"编出结论。
  **这比失败糟糕得多**——失败至少知道没做成。
- 宿主侧的人机验证与 MCP 服务**各在各的浏览器里**：用户在宿主里过了验证，服务这边的会话并没通过。

## 期望

- 拦住了就**如实说拦住了**：是"没取到内容"，不是"内容就是这样"。
- 需要人过的时候，**服务能起一个人能看见的窗口**让用户过；过完**继续这一次调用**
  （而不是让用户过完、回来重新发一遍）。
- 交互本身要有明确的授权：是用户在过，不是服务偷偷在过。

## 验收

- 请求一个会返回挑战页的地址，返回里**明确指出这是拦截**，而不是把挑战页当内容。
- 需要人工时，能起一个可见窗口；用户过完之后调用继续（同一次工具调用内，不要求用户重发）。

## 不包含

- **不做**自动破解滑块、绕过检测、第三方打码——这是明确的非目标。
- **不承诺**任何站点都能过：有的站点就是不允许非人类访问，那就如实报"过不去"。
- 不做"记住某站点的验证状态"跨会话复用（Cookie 会过期，且这属于凭据管理，另说）。
