# P-CS-01 · 符号查询（`symbols` / `list_doc_symbols`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Csharp` |
| **痛点** | [F9](../F9-分不清名字指哪个符号.md)、[F11](../F11-读大文件里的几行.md) |
| **状态** | 已实现 |
| **工具** | `symbols`、`list_doc_symbols` |

## 摘要

按**名字**而不是按位置读 C# 代码：列出一个项目里有什么类型、一个类型有哪些成员、一个成员的完整源码在原文的哪几行；
以及从本地已缓存的 NuGet 包里读它的文档符号。它解决"AI 手上有文本、却不知道这行代码在语义上是什么"这件事。

## 现状

市面上的宿主（编辑器 + agent）读代码基本只有一条路：**按路径读文本**。搜索是文本搜索，改是文本替换。
于是：

- 想知道"这个类有哪些成员"要读整个文件，几百行全进上下文（**500 行的类约 2000 tokens**，别人的项目实测过）。
- 想知道"这个方法在原文哪几行到哪几行"，得自己推——前面的文档注释、attribute、行尾注释算不算这个成员？
- 想知道"这个包提供了哪些 API"，只能靠模型记忆，而**模型会对不存在的 API 言之凿凿**（`sharp-mcp` 管这叫 NuGet 幻觉）。
- 同一个名字在语义上可能指好几个东西（同名重载、嵌套类型里的同名成员、局部函数，以及注释与字符串里的同名文字），
  文本层分不出来（详见 [F9](../F9-分不清名字指哪个符号.md)）。

## 动机

要做的是一件文本层**原理上做不到**的事：**按符号**读。

判据一句话：**要读的东西能不能用「名字」唯一确定。**

- 能 → 必须走语义层（它知道这个名字在**每一处**指的是哪个符号，也直接给得出区间）。
- 只能按位置或文本描述 → 那是**文本层**的地盘（`Resource` 的 `read` 按范围读、
  `Structured` 的 `read_structured` 按路径读）。

本仓库已经有 Roslyn 与 MSBuild 求值，缺的是把它**按符号**暴露出来。

## 非目标

- **不做**死代码检测（"这个成员没人用"）：静态分析看不到反射，误报代价高——别人的项目在这上面栽过
  （把经 JSON 序列化访问的 DTO 属性一律判成死代码）。真要给，也只能给"文本里没出现"，那是文本层的话。
- **不做** CodeFix / 自动修诊断：`dotnet format` 更专业，宿主也能直接跑。
- **不做**跨解决方案的引用分析。
- **不做**"整个工作区的符号索引"（那是 IDE 的活，成本与收益都不对）。

## 设计

**两个工具，分工是"自己的代码"与"别人的代码"：**

| 工具 | 读什么 | 怎么读 |
|---|---|---|
| `symbols` | **当前项目**里的符号 | 通过项目求值拿到编译，走 Roslyn 语义模型 |
| `list_doc_symbols` | **本地已缓存的 NuGet 包**里的 API | 从包里的 XML 文档 + 程序集读，不联网 |

### `symbols` 的三种模式

同一个工具承担"列"与"读"两态，**不增生工具**：

| 给的参数 | 得到什么 |
|---|---|
| `path` 空 + 过滤条件 | 工作区里有哪些类型（`type` / `modifier` / `nameFilter`） |
| `path` = `Ns.Type` | 这个类型的结构：成员签名，**不含实现** |
| `path` = `Ns.Type.Member(...)` | 这个成员的**签名 + 文件 + 行号区间 + 完整源码** |

成员名的写法要容忍三种输入（这是最容易出错的地方，见下"缺点"）：
**裸名**（字段、嵌套类型）、**带参数表的签名**、以及**两边空格多少**。

### `list_doc_symbols` 读的是"真实的包"

从本地 NuGet 缓存里的 `.nupkg` 取 XML 文档与程序集，回答"这个包的 1.2.3 版到底有什么"。
**不联网**——包不在本地就报"先装它"，而不是悄悄去下载。

### 预期返回 / 不返回

- **返回**：结构化的 markdown——标题带来源项目、成员带签名与区间、能带就带上文档摘要。
- **返回**：`symbols` 的"读一个成员"里带**完整实现**；`read=true` 时才带类的结构。
- **不返回**：整份文件的原文（那是 `Resource` 的 `read` 的事）；不返回"推断"出来的签名（要么拿到真的，要么说没有）。
- **不返回**：诊断/编译错误列表（那是 `confirm_draft` 预检的活）。

## 备选

- **可用的**：`MetadataLoadContext` 直接加载程序集回答"包里有什么"（`sharp-mcp` 的做法）。
  我们选了"读 XML 文档 + 程序集"，因为文档里有摘要文本，而 AI 需要的就是那句话。
- **可用的**：官方的 **Roslyn Language Server（LSP）**——功能最全，但要拉一个语言服务器进程并实现客户端，
  且它的能力面远超这里需要的。
- **不想实现的**：把 IDE 里那套"转到定义 / 查找引用 / 重命名"全盘照搬——工具数量会失控
  （别人的 Roslyn MCP 从 7 个到 92 个工具都有，说明这事没有共识）。
- **走不通的**：纯文本匹配装成语义（`skeletoken-mcp` 自己承认 `find_symbol` 是语法匹配不是语义）。
  这条对本项目**恰好相反**：我们是语义层，反而要防止退化成文本匹配。

## 缺点

- **`memberName` 的写法很不友好**（实测踩过四类）：字段与嵌套类型要**裸名**、方法要**带参数表**；
  `string?` 匹配不上（可空引用类型的 `Name` 是 `String`）；数组匹配不上（`IArrayTypeSymbol.Name` 是空串）；
  带空格就定位不到。**同一个项目的两个工具对"路径怎么写"约定还不完全一致**（`symbols` 列出来的写法
  拿去 `stage_draft` 可能定位不到）。这是当前最大的可用性缺口。
- **首次求值慢**：跑一次 MSBuild 求值拿属性与文件列表，冷启动数秒。
- **只在本仓库这种规模上验证过**：大解决方案的表现未知（别人的项目里，235 个编译项目的冷启动是 7 分钟以上）。
- **只在 Windows 上测过**。

## 待议

- **成员名解析要不要统一**：`symbols` 与 `stage_draft` 共用一套解析、并把"解析出来的实际写法"回显出来
  （实测结论是"靠裸名才稳定"）。统一是本提案之后最该做的事，但它会改两个工具的行为。
- **`path` 的匹配容错到什么程度**：忽略空格？忽略 `?`？忽略 `System.` 前缀？容错越多，误定位的风险越大。
- **一次返回多少成员**：大类型可能几百个成员。要不要分批、每批多少。
- **`list_doc_symbols` 读多大**：程序集与文档都可能是几 MB 的 XML；要不要只取某个命名空间、某个类型。
- **`symbols` 读一个成员时，要不要连它的文档注释一起给**：给了上下文更完整，也更容易撑爆返回。

## 影响

有了它，AI 可以：

- **不看整份文件就改对地方**——先看结构（便宜），再只看要改的那个成员（精确）。
- **把"这个包有什么 API"从记忆换成事实**，压制幻觉。
- **将就着做**代码审查：列出类型的结构 + 成员的实现，够看清一个文件在干什么（但不给引用关系）。

它会催生什么：**语义改名**（`rename_symbol`）直接建在它上面——名字解析一致了，改名才可能对。
它会挡掉什么：不需要再往 `read` 里塞"符号表"这类参数——那是两条路（文本 vs 符号），
两条路各自做干净比混在一起强。

## 适用

**以下情况它就不管用了：**

- **宿主自己长了语义能力**：如果编辑器侧已经能"按符号读 + 查引用 + 重命名"并把它开放给 agent
  （VS Code 的 Roslyn 能力 + Copilot 那类集成），那这一层就是多余的。
- **语言不是 C#**：`symbols` 走的是 Roslyn，写 TypeScript / Python 的项目它一点用没有。
- **代码还没能编译**：语义模型建立在"能求值出编译"之上，一个 `obj/` 都没有、也没 restore 的项目，
  它退化不成文本工具，只会报错。
- **source generator 产出的符号**：它们在任何 `.cs` 里都不存在，只活在语义模型里——
  我们能看到，但用户按文件去找会找不到。
