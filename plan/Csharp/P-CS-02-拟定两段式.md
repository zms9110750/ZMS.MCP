# P-CS-02 · 拟定两段式（`track_project` / `stage_draft` / `list_draft` / `select_draft` / `confirm_draft`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Csharp` |
| **痛点** | [F1](../改动的可信度.md)、[F5](../改动的可信度.md) |
| **状态** | 已实现 |
| **工具** | `track_project`、`stage_draft`、`list_draft`、`select_draft`、`confirm_draft` |

## 摘要

改代码不再是"直接写文件"，而是**先说清要改什么、看一遍影响、再落盘**。
第一次调用给出一份**改动清单**和一个不透明的 `cookie`；带着这个 cookie 再来一次才真正写盘。
中间任何一步都不动磁盘。

## 现状

宿主的文件写入是**一次调用、直接落盘**：给了内容就写，不问、不预览、不可撤。于是：

- AI 改代码前**看不到影响**："这个改动会不会让别处编译不过"只能靠它自己想。
- 改错了**只能再改一次**，而两次之间如果别的东西变了，第二次是**在错的基础上改**（[F1](../改动的可信度.md)）。
- **批量改造无处安放**：改 5 个地方要调 5 次写入，中途失败就是半成品，没有一个"要么全成、要么全不动"的边界。
- 失败长得像成功（[F5](../改动的可信度.md)）：写进去了但编译不过，返回里通常看不出来。

## 动机

要的是**事务性**：一组改动要么整体成立（包括"改完还能编译"），要么一个字节都不动。

现状很难，因为"能不能编译"这件事**只有编译器知道**，而编译器要跑一次完整求值；跑一次要几秒，
不能每改一行都跑。所以设计上必须把"攒"和"验"分开：**先在内存里攒够，再一次性验，最后一次性写。**

## 非目标

- **不做**通用的版本控制：这不是 git。拟定是"本次会话里一次改动的草稿"，不是历史。
- **不做**自动冲突合并：发现文件被外部改过就**交回给人**，AI 不替人裁。
- **不做**"跨项目 / 跨语言的事务"：拟定只对**一个项目**（一次 `track_project`）成立。
- **不保证**改完一定编译通过：预检给的是**诊断对比**（这次改动让错误多了还是少了），不是"保证没错"。
  一个项目本来就编译不过，工具不会因此拒绝落盘。

## 设计

### 一条链，五个工具

```
track_project(csprojPath)                     → 记下基线（文件列表 + 每个文件的指纹），给 cookie
   ↓ cookie
stage_draft(cookie, typePath, memberName, content)   → 在内存里攒一条改动（可多次）
   ↓
list_draft(csprojPath)                        → 看现在攒了哪些（不依赖 cookie，重启后靠它拿回来）
   ↓
confirm_draft(cookie, applyCookie)            → 第一次：预检；带 applyCookie 再来：落盘
   ↓
select_draft(csprojPath, memberPath, selectCookie, choice)   → 只在遇到冲突时才用
```

### 三个关键决定

**① 磁盘与内存分离。** 编辑期间**不动磁盘**——改动是内存里的"投影"，编译也拿着投影去求值。
只有 `confirm_draft` 真的写文件。这一条换来两件事：改坏了没有残留；写盘是原子的一批。

**② cookie 是当场算出来的，不是存下来的。**
- `tracking cookie`：`track_project` 给的，代表"在这个基线上改"。
- `applyCookie`：预检**当场算出**的，代表"我确认的就是这份预检结果"。落盘时再算一次比对——
  两次之间拟定变了或基线动了，就不给落。
- `selectCookie`：遇到"这个名字指好几个符号"时才给，用来选一个。
- 它们**不透明、每次都轮换**；**用它落盘之后这个 cookie 就作废了**（同一个 cookie 不能落两次）。

**③ 指纹算的是语义，不是文本。** 基线校验用的是"按符号算出来的指纹"（成员级），不是文件字节。
所以重排空行、改一处实现、`dotnet format` 之后，**只要语义没变，指纹就一致**，不会误报"被改过"。
反过来说：**确实改了内容**时它必须变。这条是刻意的——按文本比会天天误报，按字节比会被人随手格式化打乱。

### 预期返回什么 / 不返回什么

`stage_draft` 返回：
- 这次记下了什么（写入 / 替换 / 新增，改的是哪个成员）；
- **这条改动带来的诊断变化**（按 `错误码 + 消息 + 文件` 配对；行号只用于展示）——
  实测里正是这个诊断对比帮调用方提前抓到过 4 次真问题（`CS0542` / `CS0267` / `CS1519` / `CS0111`）。

`confirm_draft` 预检返回：
- **变更分类**（新增 / 删除 / 修改，各几条，分别是哪些）；
- **诊断对比**（新增若干条错误 / 消失若干条）；
- **预检查**（能不能写：路径权限、目标是不是只读、要不要新建目录）；
- 以及**落盘用的 `applyCookie`**。

`confirm_draft` 落盘返回：
- 实际写了哪些文件；
- **已落盘**（这批改动生效了）——不是"成功"两个字，而是"哪些文件变了"。

**不返回**：改动之后的完整文件内容（要看就再 `symbols` 读一次——那是另一个工具的活）。
**不返回**：对"这次改动好不好"的评价。

## 备选

- **可用的**：`dryRun` / `apply=false` 那种"一次调用里带一个开关"的做法。**不想实现**——
  开关是隐式的：调用方忘了打开就真的写了。两段式把"验"变成**必须发生过的另一段**，逼着走过流程。
- **可用的**：把改动写进一个临时文件、让用户 `git diff` 看。**不想实现**——那要求用户有 git、也在看命令行；
  而这里的调用方是 AI，它需要的是**结构化**的影响清单。
- **走不通的**：用 `MSBuildWorkspace` 打开方案再改。别人的项目在这上面吃过教训——
  它**不支持给 SDK-style 项目原地加文档**，新增一个 `.cs` 就触发整方案重载（8~10 秒），
  大方案冷启动 7 分钟以上，每个 agent 各扛 100MB+ 的 workspace。
  我们改成"跑一次 MSBuild 求值拿属性与文件列表"，编辑期间在内存里投影。
- **走不通的**：把改动**边改边写盘**。那样"改坏了没残留"和"一批原子落盘"都不成立。

## 缺点

- **多一次调用**。简单改动（改一行）也要"记基线 → 攒改动 → 预检 → 落盘"，比直接写文件啰嗦。
  这是设计换来的代价，不打算消除。
- **`cookie` 不进上下文也不落盘，丢了就得重来**（`list_draft` 能拿回拟定，但拿不回 cookie）。
  状态只存 `%LOCALAPPDATA%`，**不写进被操作的项目**。
- **基线失效的时机很粗**：现在只要落盘过，下一次工具调用就要重新求值——因为求值的缓存条件里
  带了"文件数 + 最新写入时间"（`SourceFingerprint`）。**这是刻意的**（否则刚落盘的新类型在本次会话里
  一直看不到），但确实浪费：只改内容、没增删文件时，理论上可以不重新求值。见待议。
- **`memberName` 怎么写是个坑**：见 [P-CS-01](P-CS-01-符号查询.md) 的"缺点"，两篇共用同一个缺口。
- **一次只服务一个项目**：多项目一起改要建多次拟定。

## 待议

- **落盘的两种情形要不要分开**：**新增文件**（文件列表变了）必须让缓存失效；
  **只改内容**（文件列表没变）理论上可以只刷新内容、保住求值结果。现在一视同仁，每次落盘后都要重新求值。
- **拟定的大小上限**：攒多少条改动之后建议先落一次？现在没有上限。
- **诊断对比的粒度**：现在按 `错误码 + 消息 + 文件` 配对；同一文件里同一错误的行号变了算不算同一个？
- **`select_draft` 的交互**：现在要调用方从给定的选项里挑一个（`choice`）。选项多的时候怎么呈现？
- **拟定能活多久**：进程重启后 `list_draft` 还拿得到（存在 `%LOCALAPPDATA%` 的 sqlite 里），
  但**多久之后该清理**？现在没有过期。

## 影响

有了它，AI 可以：

- **把"批量改造"当一件事做**（删 9 个 + 改 5 个 + 加 15 个），而不是十几次互不知情的写入。
- **在落盘之前就发现改坏了**——这是它最大的价值，实测里 4 次靠诊断对比提前抓到。
- **将就着做**"改动评审"：预检返回的变更分类 + 诊断对比，就是一份足够人看的改动说明。

它会催生什么：**语义改名**（[P-CS-05](P-CS-05-语义改名.md)）直接用它——改名产生的多处引用改动，
正好是"一批要么全成、要么全不动"的典型。`Resource` 的压缩包拟定（`track_archive` + `confirm`）
是它的**同一个思路在另一类对象上的翻版**，两者可以互相借鉴。
它会挡掉什么：不需要再考虑"边改边写"那套（不需要撤销日志、不需要崩溃恢复中间态）。

## 适用

**以下情况它就不管用了：**

- **宿主自己提供了事务性编辑**：如果编辑器侧能"预览一组改动 + 一起应用 + 一起回滚"并开放给 agent
  （有些 IDE 的 refactor preview 已经接近），这一层就重复了。
- **改动不在一个项目里**：跨项目、跨解决方案的改动它组织不了。
- **要改的东西没有编译**：语义指纹与诊断对比都建立在"能求值出编译"之上。
  一个裸目录（没有 `.csproj`）它直接拒绝。
- **改动需要立刻可见**：有些场景（例如生成器要读回刚写的文件）要求磁盘上马上有——
  拟定期磁盘不动，这类场景得先落盘。
