# P-CS-05 · 语义改名（`rename_symbol`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Csharp` |
| **痛点** | [F9](../F9-分不清名字指哪个符号.md)、[F1](../F1-别人改了文件.md) |
| **状态** | 已实现 |
| **工具** | `rename_symbol` |

## 摘要

改一个符号的名字，**只改真正引用这个符号的地方**。
它不靠在文本里替换，而是走语义层认符号；改动的多处引用落成**一份拟定**，确认了才一起写盘。

## 现状

文本替换会把**同名但不同**的东西一起改掉：另一个类里也叫这个名字的方法、注释里提到的名字、
字符串字面量里的名字（而这常常是要保留的：反射用的名字、配置键、日志标签）。
反过来，该改的地方又**会漏**：`nameof(...)` 里的引用、另一个 `#if` 分支里的引用。

一次错误的批量改名**很难看出来**——diff 里全是名字，改多改少都不显眼。

## 动机

改名是**语义操作**：核心不是"把这段文本换掉"，而是"找出所有引用**这个符号**的位置"。
这个判断只有语义层做得到（[F9](../F9-分不清名字指哪个符号.md) 里逐条列了为什么文本层做不到）。

而改名的**形状**又特别适合拟定：一处改名会同时改好几个文件、每个文件好几处，
一次要么全成、要么全不动的边界非常自然。

## 非目标

- **不做**"改文件名"：改的是符号（类型、成员），不是磁盘上的文件。
- **不做**"改命名空间"顺带搬目录：C# 里命名空间与目录不强制对应，跟着搬反而出意外。
- **不做**重命名重构里的**接口成员连带**（改接口方法名要不要一并改实现类）：
  那是一个判断，不是一次替换。工具只改**这一个符号的引用**，剩下的调用方自己决定。
- **不做**批量改名（一次改多个符号）：一条拟定一个符号，混在一起说不清"这次改的是哪个"。

## 设计

**三步，与 [P-CS-02](P-CS-02-拟定两段式.md) 共用同一条链：**

```
track_project(csprojPath)              → 拿 tracking cookie
   ↓
rename_symbol(cookie, memberPath, newName)
        → 语义层找出所有引用，落成一份拟定，返回"改名清单"：
          拟改哪几个文件、每个文件里改哪几处、哪些地方**明确不动**（同名但不同符号）
   ↓
confirm_draft(cookie, applyCookie)     → 预检（诊断对比）→ 带 applyCookie 落盘
```

**关键在"明确不动"这一节。** 返回里要**点名**那些"名字相同但不是它"的位置，
让调用方看得见"工具确实做了语义判断"，而不是把 diff 丢过去让人自己核对。

**改动的分类**与拟定一致：`修改`（这个引用改了）。如果改名同时引起诊断变化（例如与别的类型撞名了），
诊断对比会显示出来。

### 预期返回什么 / 不返回什么

**返回**：拟改的文件与位置清单；**不会碰**的同名位置清单；随后的诊断对比。

**不返回**：改名之后的完整文件（要看去 `symbols` 读）。
**不返回**：对"这个名字起得好不好"的评价。
**不返回**：一个"已改名"就完事的结论——改名是拟定，必须走确认。

## 备选

- **可用的**：让调用方自己用 `grep` + 批量替换。**不想实现**——那正是这条痛点本身，
  工具存在的理由就是替代它。
- **可用的**：把改名做成 `symbols` 的一个参数（`symbols(path=..., rename=...)`）。
  **不想实现**——`symbols` 是只读工具（`ReadOnly = true`），一个工具混着只读与破坏性两态，
  注解就没法诚实（MCP 的注解是**按工具静态**的，表达不了"只有某个参数时才具破坏性"）。
- **走不通的**：用文本层近似语义（拿"名字出现的地方"当"引用这个符号的地方"）。
  实测里这个近似**两头都错**：多改注释与字符串、漏掉 `nameof`。
- **走不通的**：不建拟定、直接改。改名的改动跨文件，中途失败会留下**半改完的代码**
  （一半引用改了、一半没改），那比不改还糟。

## 缺点

- **一次只改一个符号**：大重构要来回好几次。
- **依赖 `memberPath` 的写法**：和 [P-CS-01](P-CS-01-符号查询.md) 共用同一个缺口——
  路径写不对就定位不到，而"定位不到"与"没有这个成员"要能分开（见待议）。
- **不处理接口连带**：改接口方法名以后，实现类里会留下"没实现接口"的错误——
  这个错误由**诊断对比**暴露给调用方，工具自己不修。
- **改名的"不碰清单"可能很长**：一个常见名字（`Id`、`Value`）在同项目里可能几十处同名不同符号，
  返回会臃肿。

## 待议

- **`memberPath` 的容错**：与 [P-CS-01](P-CS-01-符号查询.md) 统一解析的那一刻，这里一并解决。
- **定位不到时怎么办**：现在报"定位不到符号"。要不要顺便给"最接近的几个候选"
  （编辑器的"你是不是想找……"）？给了会更容易一次改对，也可能把调用方带偏。
- **"不碰清单"什么时候省略**：同名位置太多时（例如五六十处）要不要折叠成一句"另有 N 处同名但不是它"。
- **改私有成员要不要更严**：私有符号的引用范围本来就小，风险低；公开符号的改名影响面大。
  要不要针对公开符号要求额外的确认。
- **与 `select_draft` 的关系**：改名遇到"这个名字指好几个符号"时，走 `select_draft` 选一个——
  这条链现在是通的，但交互（怎么呈现选项）与 [P-CS-02](P-CS-02-拟定两段式.md) 的待议是同一件事。

## 影响

有了它，AI 可以：

- **安全地做重构的第一步**：改名是几乎所有重构的开头（"先把它改个说得清的名字"）。
- **将就着做**"符号被用在哪"的地图：定义改名要改哪些地方，等于给出了这个符号的引用面
  （虽然不是一次完整的"查引用"）。

它会催生什么：**"查引用 / 查调用者 / 查实现类"** 这几个只读能力。
改名已经证明语义层能算出引用面，把这些暴露出来只差一层输出格式。
它会挡掉什么：不需要再考虑"文本批量替换 + 人工核对"那条工作流。

## 适用

**以下情况它就不管用了：**

- **宿主自己带语义改名**：VS Code / VS / Rider 的 Rename 就是这个能力，如果开放给 agent，这层是重复的。
- **引用跑到项目外**：一个公开 API 被别的仓库引用，改名只能改本项目的引用——
  剩下的破坏由编译错误暴露（工具不做跨仓库分析）。
- **代码编译不过**：语义模型建不起来时，它退化不成文本工具，只会报错。
- **名字本身在字符串里被反射使用**：`Type.GetType("Old.Name")` 这种，语义层也看不见——
  这是 C# 的固有限制，不是这个工具的缺陷，但会让人以为"改名很安全"而踩到。
