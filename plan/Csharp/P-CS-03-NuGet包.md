# P-CS-03 · NuGet 包（查 / 装 / 卸 / 文档符号）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Csharp` |
| **痛点** | [F9](../F9-分不清名字指哪个符号.md)（"这个包到底有什么 API" 是它的前一半）、[F1](../F1-别人改了文件.md) |
| **状态** | 已实现 |
| **工具** | `list_project_packages`、`search_packages`、`list_package_versions`、`get_package_metadata`、`install_packages`、`remove_packages`、`list_doc_symbols` |

## 摘要

围绕 `csproj` 的包管理：看项目现在装在用什么、去 nuget.org 搜、看某个包有哪些版本、装、卸；
以及从**本地已缓存**的包里读它的真实 API 与文档符号。解决"AI 对包版本和 API 全靠记忆"这件事。

## 现状

- **模型会对不存在的 API 言之凿凿**（`sharp-mcp` 把它叫作 NuGet 幻觉）：它记得"这个包大概有这个类"，
  但记不清是哪个版本、参数是什么、这个版本有没有。
- 查包要联网、要走 HTTP、要解析 JSON，宿主没有这项能力；**手写 `curl` 进上下文既慢又脏**。
- **装包这件事不只是改一行**：`<PackageReference>` 之外还牵涉版本冲突、传递依赖、目标框架兼容性、
  `obj/project.assets.json` 的同步——这些都在模型的视野之外。
- 搜到的包名**不完全可信**（近似名、已废弃包、拼写相近的恶意包），需要"看它的元数据"这一步。

## 动机

把"查包"和"装包"从**记忆**换成**事实**，并且让装包这件事**在拟定里发生**（与 [P-CS-02](P-CS-02-拟定两段式.md) 同一套纪律）。

联网部分只去一个地方：**nuget.org**。这是刻意的——不认私有源、不认自定义地址，
范围窄了才能把"安全"说清楚。

## 非目标

- **不做**私有源 / 企业源（`nuget.config` 里的自定义 source）：这是明确的取舍，见"缺点"。
- **不做**包的分析（许可证合规扫描、漏洞扫描）。
- **不做**"升级到最新版"这种批量动作：升级是**有风险的判断**，工具只给"有哪些版本"，不替你选。
- **不缓存**包搜索的结果到跨会话：搜索结果时效性强（[F3](../F3-同一地址读两次.md) 那套缓存用在这里是错的）。

## 设计

### 七个工具，四个动作

| 动作 | 工具 | 联网？ |
|---|---|---|
| 看项目现在装了什么 | `list_project_packages` | 否 |
| 搜包 | `search_packages`（`page` 翻页） | 是（仅 nuget.org） |
| 看有哪些版本 | `list_package_versions`（`local` / `web` 两态） | 视参数 |
| 看一个包的元数据 | `get_package_metadata` | 是 |
| 装 / 卸 | `install_packages` / `remove_packages` | 是（装）/ 否（卸） |
| 读包的 API 与文档 | `list_doc_symbols` | **否**（读本地缓存） |

**`list_package_versions` 的两态合一**：`local=true` 看本地缓存里有哪些版本，`web=true` 去 nuget.org 看。
这样调用方不必分辨"我该调哪个工具"，而是说清"我想看哪儿"。

### 装 / 卸**不走**拟定

`install_packages` / `remove_packages` 的关键词是 **Destructive = true, Idempotent = false**——
它们改的是项目文件，且**不是**幂等的（同一个包装两次是不一样的）。

**但它们不进拟定**：拟定管的是"读现状 → 决策 → 写回"那种**基于快照**的改动；
而装包是**现读现改的命令行**（`dotnet add/remove package`），不存在"基于过期快照覆盖"的问题，
所以它立刻改盘、不可回滚。这是刻意的分工，不是漏做。

装完之后紧接着给**这个版本的 API 摘要**——不是额外一次调用，而是**一条链**：
装了包，下一步一定是"它有什么"，那么就在同一次动作里把 `list_doc_symbols` 该给的东西带上。

### 预期返回什么 / 不返回什么

**返回**：包名 + 版本 + 目标框架这些**可核对的事实**；`search_packages` 返回候选清单（带下载量/是否已废弃这类判断依据）；
`list_doc_symbols` 返回类型与成员的签名 + 文档摘要。

**不返回**：推荐哪个版本（工具不给建议）；不返回"这个包好不好"；
不返回许可证分析；**不返回臆测的 API**——包不在本地就说"先装它"，不猜。

## 备选

- **可用的**：直接把 `dotnet add package` 包一层。**不想实现**——那样返回的就是命令行文本，
  而调用方需要的是结构化的"装了什么、变成什么样"。
- **可用的**：`MetadataLoadContext` 加载程序集回答"包里有什么"（别人的做法）。
  我们读 XML 文档 + 程序集，因为**文档里有摘要文本**，那正是 AI 需要的。
- **走不通的**：支持 `nuget.config` 里的任意源。一旦允许自定义地址，就得回答"哪些源可信"、
  "包名冲突时用谁"、"要不要签名校验"——这几个问题都没有好答案，所以范围收到只认 nuget.org。
- **走不通的**：把搜索/版本查询也塞进本地缓存。包是**会被撤回、会被重新发布**的（unlisted / 重推），
  缓存下来等于给调用方一个"曾经是这样"的事实。

## 缺点

- **只认 nuget.org**：公司私有源的包它装不了，这是最常被问到的限制。
- **联网动作没有预览**：`search_packages` 与 `get_package_metadata` 直接发请求。它们只读，但**慢**，
  且会暴露"这个访问了外网"这件事（注解里 `OpenWorld = true`）。
- **装包会改 `obj/`**：`project.assets.json` 会变，于是下一次求值必然发生（与 [P-CS-02](P-CS-02-拟定两段式.md) 的缓存那件事同一处）。
- **卸载比装载脆弱**：卸载要判断"还有谁依赖它"（传递依赖），而现在这块判断很薄。
- **`list_doc_symbols` 的输出可能很大**：一个大包的 API 可能上千个符号。

## 待议

- **一次搜索给多少个结果**（`page` 的页大小）。
- **`list_doc_symbols` 一次给多少符号**：按命名空间切？按类型切？现在没有上限。
- **安装多个包时的顺序**：现在是一次装一批（`nugetPack` 是数组）。批内某个失败时，
  已经装上的要不要回退？（拟定能覆盖落盘，但"dotnet add"本身会写 `obj/`。）
- **版本区间的写法**：`verRange` 支持到什么程度（`[1.0,2.0)` 这种）现在没有明确定义。
- **搜到的包要不要提示"可能拼错"**：近似名是供应链攻击的常见入口。

## 影响

有了它，AI 可以：

- **在写代码之前先确认 API 存在**——这把"幻觉"从"肯定会发生"降成"偶尔发生"。
- **将就着做**依赖审计：`list_project_packages` + `list_package_versions` 能看出"这个项目用的版本有多旧"。

它会催生什么：`list_doc_symbols` 与 [P-CS-01](P-CS-01-符号查询.md) 是**同一个能力的两半**
（自己的代码 / 别人的代码），将来如果把"读别人的代码"这条路走通（例如读 GitHub 上的源码），
两者会在同一个入口下面汇合。
它会挡掉什么：不需要再考虑"让模型自己记住包 API"这类提示词工程。

## 适用

**以下情况它就不管用了：**

- **宿主自己带了包管理**：如果编辑器侧能直接装包、能给出 API 补全（VS / Rider 都能），
  这一层的边际价值就落在"把能力开放给 agent"这一点上。
- **私有源 / 离线环境**：只认 nuget.org，这条就没戏。
- **不是 .NET 项目**：`csproj` 之外的包管理（npm / pip / cargo）它一概不管。
