# P-CS-04 · 工作区与解决方案（扫 / 看 / 增删 / 迁移 / 改元数据）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Csharp` |
| **痛点** | [F5](../F5-失败了却像成功.md)（"没扫到"必须与"没有"分开）、[F1](../F1-别人改了文件.md) |
| **状态** | 已实现 |
| **工具** | `scan_projects`、`view_project_or_solution`、`add_project_to_solution`、`remove_project_from_solution`、`migrate_solution_to_slnx`、`edit_project_metadata` |

## 摘要

在一个目录里找到有哪些解决方案与项目、看清一个项目是由哪些文件声明出来的，以及**编辑解决方案本身**：
加项目、删项目、把 `.sln` 迁移成 `.slnx`、改项目文件的元数据。

## 现状

- 想知道"这个工作区里有什么"要自己列目录再猜——`ls` 出来的是一堆文件，不是"解决方案与它的项目树"。
- **一个项目的声明不只是一份 `.csproj`**：`Directory.Build.props` 会向上影响它、
  `.props` / `.targets` 会通过 `Import` 参与、`obj/` 里的中间文件决定它的属性。
  只看 `.csproj` 会得到**残缺**的图景。
- 编辑解决方案要开 IDE；命令行 `dotnet sln` 能做一部分，但拿回来的是**文本输出**，
  而调用方需要的是"加完之后方案变成什么样"。
- `.sln` 是旧格式（XML 之外的一套自定义语法），`.slnx` 是新格式——**两者不是一个东西**，
  混着改会得到一个两边都不认的文件。
- **改元数据（`TargetFramework`、属性、`PackageId` 之类）是改 XML**，而 XML 改起来最怕的是
  "改完之后整个文件的格式都变了"（[F10](../F10-结构化文档只能整份重写.md) 是同一个问题的泛化版）。

## 动机

把"工作区长什么样"和"方案怎么改"变成**结构化的、可核对的事实**，而不是靠调用方从目录列表里推。

关键的取舍是：**凡是 MSBuild 知道的事，问 MSBuild，不要猜**——
`obj/` 在哪、哪些文件参与声明、某个属性求值成什么，都不能硬编码。

## 非目标

- **不做**通用命令行通道（不做"帮我把这条命令跑了"）。`dotnet new` 这类"参数无限"的操作也不包成工具
  ——一个工具不可能把无限的可能性描述清楚，硬包出来的 `create_project` 已经被删过。
- **不做** `.sln` 的完整解析与重写（只做"迁移到 `.slnx`"这一件事）。
- **不做** MSBuild 属性的全量查询接口（那会变成一个裸的 MSBuild 客户端）。
- **不做**目录树的可视化。

## 设计

### 六个工具，三组

| 组 | 工具 | 什么性质 |
|---|---|---|
| 扫与看 | `scan_projects`（按 `depth` 递归找）、`view_project_or_solution` | 只读 |
| 改方案 | `add_project_to_solution`、`remove_project_from_solution`、`migrate_solution_to_slnx` | 改 `.slnx` |
| 改项目 | `edit_project_metadata` | 改 `.csproj`，**走两段式** |

### ① 问 MSBuild，不硬编码

- **`obj/` 的位置**：一律问 `MSBuildProjectExtensionsPath` / `ProjectAssetsFile`，**不硬编码** `<项目目录>/obj/`。
  本仓库自己的构建输出就被重定向到别处，硬编码在**这个仓库里**就已经是错的。
- **哪些文件参与声明**：`view_project_or_solution` **跟随最近的 `Directory.Build.props` 自己的 `Import`** 向上列出。
- **未知就是未知**：求值拿不到时输出 `(obj 的位置未知)` 这样的话，**不**编一个看起来合理的路径。

### ② 编辑方案只允许 `.slnx`

`.sln` 先迁移（`migrate_solution_to_slnx`），之后再编辑。这样工具只用面对**一种**方案格式，
不用维护两套解析与两套序列化。

### ③ 改元数据走两段式

`edit_project_metadata` 与 [P-CS-02](P-CS-02-拟定两段式.md) 是同一套纪律：
第一次给"会变成什么样"，带上 `cookie` 再来才落盘。
（本仓库里走两段式的只剩它和 `confirm_draft` 两处——其余都收敛到了拟定这一条主链上。）

### 预期返回什么 / 不返回什么

`scan_projects` 返回**每个解决方案一块**：`<解决方案路径>(被描述数+额外数)`，接着是它描述的项目树
（`├─` / `└─`），再接着"在该解决方案文件夹下、但没被它描述"的项目（`-` 前缀）；不被任何解决方案覆盖的
项目在最后平铺。`bin` / `obj` / `.git` 跳过。

**返回**：项目树、项目声明的文件清单、方案改动前后的对照、元数据改动前后的对照。

**不返回**：**一个项目都没扫到时，只有一行（明确说没扫到）**——不返回空、也不返回"看起来像结果的东西"。
不返回 MSBuild 的原始输出（那是调试信息，不是给 AI 的事实）。
**不返回**猜测：求值不出来的属性老老实实标"未知"。

## 备选

- **可用的**：直接调 `dotnet sln` / `dotnet msbuild` 然后**把它的文本输出返回**。
  **不想实现**——调用方要的是结构，不是一段给人看的输出；而且命令行输出里的失败常常混在成功里。
- **可用的**：支持 `.sln` 与 `.slnx` 双格式。**不想实现**——两套格式两套坑，
  而迁移只需要一次；把"迁移"本身做成工具比"两边都支持"便宜得多。
- **走不通的**：用 `MSBuildWorkspace` 打开方案拿"完整的语义视图"。别人的项目在这上面吃过教训
  （冷启动、加文件触发全量重载、内存），而且我们要的只是**属性与文件列表**，
  跑一次求值（一个进程，拿到输出）比打开 workspace 便宜两个数量级。
- **走不通的**：把解决方案的编辑也放进拟定。
  拟定是"内存里投影一份编译"，而解决方案的改动**不产生可编译的投影**（它只是改了个项目清单），
  硬塞进去会让"拟定"这个概念变得不清不楚。这里用更轻的两段式（预检 → 带 cookie 落盘）。

## 缺点

- **`.sln` 必须先迁移**：老仓库上手第一件事是迁移，多一步。
- **`scan_projects` 的输出是给人看的样子**（带树的制表符）。它照顾了可读性，代价是**不易解析**
  （如果调用方想程序化地用它）。
- **`depth` 是个魔数**：递归多深？太浅找不到，太深很慢（见待议）。
- **`edit_project_metadata` 的 `content` 是 XML 片段**：改元数据要知道 XML 的写法，
  而这不是所有调用方都熟的（`Structured` 那边的 `edit_structured` 才按路径改）。
- **求值有代价**：每次 `view_project_or_solution` 都可能触发一次 MSBuild 求值（几秒）。

## 待议

- **`scan_projects` 的 `depth` 默认值**：现在默认递归，深目录会慢。
- **扫到多少个就停**：大仓库里解决方案可能几十个，要不要上限。
- **`edit_project_metadata` 与 `Structured` 的边界**：改 `csproj` 里一个属性值，
  用 `edit_project_metadata`（带两段式，但要知道 XML）还是 `edit_structured`（按路径改，但没有项目语义）？
  两条路都在，选哪条没有定论。
- **`view_project_or_solution` 要不要给"这个属性是从哪个文件来的"**：向上跟随 `Import` 时拿到了链，
  但只列了文件，没有"这条属性来自哪一份"。

## 影响

有了它，AI 可以：

- **在不读任何代码的情况下说清"这个工作区长什么样"**——方案、项目、它们的关系。
- **将就着做**"项目体检"：`view_project_or_solution` 能看出目标框架、包引用、属性从哪继承来的。

它会催生什么：`Structured` 的 `edit_structured` 与它**在同一个交叉点**上（"改 XML 的一个值"），
将来这两条路会合成一条（见待议）。
它会挡掉什么：不需要再考虑"给命令行操作包一层工具"——
那条路已经试过并放弃了（`create_project` 被删掉就是一个标记）。

## 适用

**以下情况它就不管用了：**

- **宿主自己就是 IDE**：VS / Rider 对解决方案与项目的理解远超这一层，如果它能把这些开放给 agent，
  这一层就没必要。
- **不是 .NET 的工作区**：它只认 `.csproj` / `.slnx`。
- **方案复杂到求值都跑不动**：MSBuild 求值失败（缺 SDK、缺 restore、有自定义 target 报错）时，
  它给出的会是"未知"而不是结果——这是设计如此，但也就意味着**在这种工作区里它帮不上忙**。
