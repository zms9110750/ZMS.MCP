# P-WF-01 · 工作流生成（`list_workflow_schema` / `write_workflow` / `validate_workflow`）

| | |
|---|---|
| **项目** | `src/ZMS.MCP.Workflow` |
| **痛点** | **没有直接对应的痛点**（近的是 [F9](../F9-分不清名字指哪个符号.md) 与 [F10](../F10-结构化文档只能整份重写.md)：都是"改一份有结构的东西"） |
| **状态** | 已实现 |
| **工具** | `list_workflow_schema`、`write_workflow`、`validate_workflow` |

## 摘要

用**一棵强类型树**生成 GitHub Actions 工作流 yaml：树 → 校验 → 确定性写盘。
同一棵树两次生成，字节一致。顺带能查"这棵树能怎么长"（触发器、字段、常用 action 的取值域），
也能校验一份已有的 yaml。

## 现状

- **模型写工作流靠记忆**：触发器的名字、`strategy.matrix` 的写法、`needs` 与 `outputs` 的配合、
  `uses` 要不要带版本——这些它记得大概，写出来常常差一点。而工作流**跑在 CI 上**，
  错了要等到触发才知道。
- **手写 yaml 容易在缩进与标量上翻车**：多行 `run:` 被写成折叠标量（`>-`）会把三行脚本折成一行，
  **语义直接变了**（这是我实现这套工具时自己踩到的）。
- **校验没有手段**：官方解析器是 **TypeScript** 的（`@actions/workflow-parser`），
  早期那个 Go 版仓库已经不存在；C# 侧没有官方实现。
- **生成与手改混着来**：工作流里既有生成的部分也有人加的一段，下一次生成就把它冲掉。
- 工作流是**格式最严的一类文本**：它没有注释的自由、缩进即语义，而 AI 改文本时的容错几乎为零。

## 动机

把"写工作流"从**文本生成**换成**结构生成**：

- AI 给的是**有类型的树**（而不是一段 yaml），缩进与标量由生成器负责——它还附带校验；
- 生成的 yaml **确定性**（同一棵树字节一致），因此可以进版本控制、可以回归测试；
- 这一层的能力面（触发器有哪些、某个 action 有什么输入）由工具回答，不靠模型记忆。

**"给 AI 的强类型架构"不另外写一份 schema**：MCP 工具的 `inputSchema` 本身就是——
树是工具自己的参数，客户端列出工具时就能看到它的完整 JSON 架构。

## 非目标

- **不做**读回 / 往返（把 yaml 解析回树再生成一遍）。生成是单向的；要校验已有 yaml 有 `validate_workflow`。
- **不做**官方 action 的完整目录（几百个 action 的输入）——只列最常用的几个，
  其余靠 `list_workflow_schema` 说清"这不在我的范围里"。
- **不做**表达式求值（`${{ }}` 里能写什么）——表达式原样写进 yaml，工具不解析它。
- **不做**多个工作流之间的编排、不做 CI 的本地模拟（不在本地跑工作流）。
- **不做**非 GitHub 的 CI（GitLab CI / Jenkins）。

## 设计

### 三个工具

| 工具 | 干什么 |
|---|---|
| `list_workflow_schema` | `kind`（`trigger` / `field` / `action`）+ `value` 定位节点，回答"能怎么写" |
| `write_workflow` | `path` + `tree` → 先校验 → 确定性写 yaml |
| `validate_workflow` | `path`（读已有 yaml）或 `tree`（直接给树），二者给一 |

分工的道理：**树的结构**由 `inputSchema` 说（协议自带），**取值域**（哪些触发器、哪些字段）
由 `list_workflow_schema` 补——schema 表达得了形状，表达不了"这个位置能填哪些名字"。

### 强类型树的覆盖范围

- **触发器 35 个**：6 个形状特殊的单独建模（`push` / `pull_request` / `workflow_dispatch` /
  `schedule` / `workflow_call` / `workflow_run`），其余 29 个通用形状的走一个**开放字典**
  （`types` / `branches` / `paths` / `tags` 几档过滤）。开放字典是为了**官方加事件不用改模型**。
- **常用 action 只列 4 个**（checkout / setup-dotnet / upload-artifact / download-artifact）。
- **`strategy.matrix` 两种形态都支持**：把取值列出来，或者交给表达式
  （`fw: ${{ fromJson(needs.build.outputs.tfm_json) }}` —— 真实工作流里就是这么写的）。

### 确定性是硬要求

"稳定"指的是**同一棵树生成的结果永远一样，可回归测试**：

- **键序固定**：不依赖字典 / 反射的枚举顺序（用有序字典，或代码里的固定顺序）；
- **缩进固定 2 格**；
- **行尾一律 LF**（生成器把换行归一——生成它的那个库在 Windows 上默认给 CRLF）；
- **多行内容用块标量**（`|`）：折叠标量（`>-`）会把换行折成空格，那会改变脚本语义。

### 落盘遵守两段式

`write_workflow` 与 [F1](../F1-别人改了文件.md) 一致：

- **目标不存在** → 直接写（没有"别人"可覆盖）；
- **目标已有内容、没给凭据** → **不写**，把"这份内容会被**整份替换**、不可回滚"摆出来；
- **给了凭据且对得上** → 写；对不上 → 不写，报现状。

写完之后返回**新文件的凭据**，下次要改带上它。

### 预期返回什么 / 不返回什么

- **返回**：`list_workflow_schema` 返回取值域（markdown）；`write_workflow` 返回写了哪儿 + 凭据；
  `validate_workflow` 返回问题清单（schema 层 + 语义层）。
- **返回**：校验要分清两类——**schema 问题**（缺 `runs-on`、`uses` 与 `run` 同时给）
  与**语义提示**（`needs` 指向不存在的作业、依赖成环）。
- **不返回**：生成之后的 yaml 全文（它就在那个文件里；要看就 `read`——那是另一个工具的活）。
- **不返回**：把"能跑"说成保证——校验只覆盖 schema 与语义，跑不跑得起来是 CI 的事。

## 备选

- **可用的**：**fork 现成的 C# 模型库**（`samsmithnz/GitHubActionsDotNet`：手写的强类型模型 +
  YAML 序列化，MIT）。**不想实现**——它的模型覆盖取决于作者跟进，而且它输出的**确定性没有验证过**；
  我们要的"字节一致"是硬要求，不能建立在一个没验证的保证上。参照它、自己写反而更短。
- **可用的**：**用官方 `workflow-v1.0.json`**（微软自定义 DSL，99 KB，覆盖 ~35 个触发器）
  **直接当"给 AI 的架构"**。**不想实现**——它不是标准 JSON Schema（喂不了通用校验器），
  可读性差（`-strict` / `-mapping` / `-activity` 变体噪声大），不适合给人或模型看。
  它适合当**参照**（我们建模时对着它补字段）。
- **走不通的**：**复用官方解析器做校验**（`@actions/workflow-parser`，npm）。
  它是 TypeScript/ESM，要在一个 .NET 服务里拉一个 node 进程——重，而且校验结果还得跨进程搬回来。
- **走不通的**：**手写 yaml 字符串**（不用库）。多行折行、引号转义、特殊字符这些规则自己写会一直漏；
  用库的 emitter 只把**我们控制的**部分（键序、缩进、多行样式）钉死，其余交给它。

## 缺点

- **覆盖是"常用集"**：触发器做全了，但 **action 只列 4 个**。碰到没建模的 action 输入，
  调用方得自己知道怎么写（`with` 是开放字典，写什么都能进去，但工具给不了提示）。
- **不读回**：不能"打开一份 yaml、改一处、再生成"——生成是单向的。
  已有的工作流要改，得**在树里重建它**（或者手工改那段 yaml，然后用 `validate_workflow` 校验）。
- **树很深**：`jobs.<名>.steps[].with.<键>` 这样的路径写起来长，`inputSchema` 也因此很大
  （这是"强类型"的代价）。
- **确定性依赖实现的自觉**：键序、缩进、LF、块标量这四条都是**行为约定**，
  任何一条被破坏，"字节一致"就没了（现在有回归测试盯着，但测试只覆盖了构造出来的样例）。
- **只用四种格式**里最简单的场景验证过：没测过超大工作流、没测过所有 35 个触发器的组合。

## 待议

- **常用 action 要不要扩**：现在是 4 个。扩到多少为止？给"所有 action"显然不现实
  （那要动态拉几百个 `action.yml`）。
- **`strategy.matrix` 的表达式那一档**：现在单独一个字段（`matrixExpression`）承载，
  与"列出取值"那一档并列。这个形状要不要合并成一个更自然的写法。
- **`write_workflow` 的凭据口径**：现在只有元数据段（路径 + 大小 + 修改时间），没有内容段——
  因为改的是整份文件、不需要内容级比对。这与 [P-RS-02](../Resource/P-RS-02-本地写.md) 的口径**不完全一致**
  （那边有内容段），要不要统一。
- **`list_workflow_schema` 的 `kind` 要不要加**（现在三个：trigger / field / action）。
- **校验的深度**：现在有 schema 层 + 语义提示两层。要不要再加"这个表达式引用的东西存在吗"
  （那需要解析 `${{ }}`，而现在是非目标）。
- **要不要支持"读回 + 保留原样"**（把没有建模的部分原样透传）——那会让它从"生成器"变成"编辑器"。

## 影响

有了它，AI 可以：

- **把工作流当结构写**，不再靠记忆拼 yaml——这一步把"缩进/标量/名字记错"这类错误挡在了生成之前。
- **确定性生成**：生成物进版本控制不会天天变（没有"这次生成的键序刚好不同"）。
- **将就着做**"工作流体检"：`validate_workflow` 能挑出缺 `runs-on`、依赖成环这类问题，
  对一份手写的工作流也有用。

它会催生什么：**"由结构生成文本"这个模式的第二个用例**——它与
[P-CS-02](../Csharp/P-CS-02-拟定两段式.md)、[P-RS-04](../Resource/P-RS-04-压缩包.md) 是同一族的思路
（把改动先在内存里装配好、确认了再落盘）。将来如果 `Structured` 那边也要"由树生成文档"，
这三处应当共用同一套"确定性序列化"的纪律。
它会挡掉什么：不需要再考虑"给模型一段工作流模板让它填空"——模板填空在缩进上一样会翻车。

## 适用

**以下情况它就不管用了：**

- **宿主自己会写工作流**：如果编辑器侧已经带 GitHub Actions 的补全与校验（VS Code 的官方扩展就能做），
  这一层的增量只剩"确定性生成"与"树作为参数"。
- **要生成的是别的 CI**：只认 GitHub Actions。
- **工作流里用了大量未建模的 action 输入**：`with` 虽然是开放字典，但工具给不了提示，
  调用方还是得自己知道那些输入叫什么。
- **要改一份已有的、复杂的工作流**：生成是单向的，重建那棵树可能比手工改 yaml 还费事——
  这种场景 `validate_workflow` 比 `write_workflow` 更有用。
