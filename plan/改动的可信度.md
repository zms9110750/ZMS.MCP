# 改动的可信度（F1 / F2 / F5）

这一组是**同一件事的三个面**：*"改动"这个动作可不可信*。

- **F1** —— 改之前，我知不知道这东西已经不是我读的那一份了？
- **F2** —— 删掉之后，还能不能找回来？
- **F5** —— 没做成的时候，看不看得出来？

三条各自独立成立（各自有自己的场景、自己的验收），但都指向同一个问题，
所以**写在一个文件里**——不再用"相关"去跨文件串它们。

---

## F1 · 别人改了文件，AI 不知道

| | |
|---|---|
| **状态** | 已解决（`Resource` 的凭据两段式、`Csharp` 的拟定基线校验） |
| **涉及** | Resource、Csharp、Workflow |

### 背景

AI 读了一份文件、想好要改哪几处，等它把改动交回去的时候，**这份文件可能已经不是它读的那一份了**——
用户在自己编辑器里改了、另一次工具调用改了、`dotnet format` 跑过、`git checkout` 换过分支。

AI 看不到这些。它手里的"上下文里的那一份"是**过去的快照**，而它以为那是现在。

### 现状

- 宿主（编辑器）自带的能力里，`write_file` 是**整份覆盖**：AI 把"它记忆里的全文 + 一处改动"写回去，
  中途别人的改动就被**静默抹掉**。这是最常见的一种损坏，而且**不回滚**。
- 文件系统本身不提供"我上次看到的版本"这个概念；`mtime` 有，但没人拿着比对。
- 市面上的 MCP 文件工具基本都是"路径进、内容出"，没有一个是**两段式**的。
- 本仓库原有的 `Csharp` 侧有一半：拟定的基线校验（`track_project` 记基线，`confirm_draft` 落盘前比对）。
  但那只是**一个项目内的一条链路**；`Resource` 的读写、`Workflow` 的落盘当时都没有。

### 期望

改动**已有的**东西时，调用方必须能证明"我知道我要改的是什么"：

- 读过之后拿到一个**不透明的短标识**，改的时候带回来；
- 对不上就**不执行**，并把"现在是什么样"报出来（而不是替谁猜）；
- 缺标识、标识过期，都算**两段式的正常第一段**，不算失败。

### 验收

- 一份文件被外部改动后，带旧标识的改动请求**被拒绝**，且返回里能看出"这期间它被改过"。
- 只读了元数据（没读全文）就能拿到的标识，与读过全文的标识**能互相校验**（前者不该因为缺内容段而被拒）。
- 检测到"文件不存在"这一档也能表达：新建走它，覆盖已有文件不认它。

### 不包含

- **不做**"改了之后自动合并"——发现冲突就交回给人，AI 不替人裁。
- **不管**"压缩包被外部改动"这类组合场景：那是本条与 F6 的交叉，落进各提案的**设计**一节，
  不单独立一条痛点（没人会先想到"改包要先看包变没变"）。
- 不做文件系统的实时监听 / 订阅。

## F2 · 删了就没了

| | |
|---|---|
| **状态** | 已解决（`Resource` 的删除走回收站，进不了回收站就不执行） |
| **涉及** | Resource |

### 背景

删除是**唯一不可逆**的常规操作。改错了还能看出改了什么、再改回来；删错了，内容就不在磁盘上了。

AI 删东西的理由通常很短："这个文件看起来没用了"。而它判断"没用"的依据，通常是**一段文本里没出现这个名字**——
这不等于"没人用"。

### 现状

- 命令行里的删除是**直接抹掉**（`Remove-Item -Force` / `rm -rf`）：不进回收站、不问、不报告删了什么。
  一个被授权的 agent 顺手跑一句就没了。
- 图形界面的删除走回收站，但那需要人点。
- 宿主的 `write_file` 能覆盖内容，但**没有"删除"这个动作**——于是 agent 想删就从命令行绕，绕过去就是硬删。
- 远端（FTP）**没有回收站这个东西**，删了就是真没了。

### 期望

- 本地删除**默认走回收站**，并告诉用户"去哪能找回"。
- **进不了回收站的情形**（文件过大、网络盘、可移动盘、只读卷）**不执行**，报出来交用户手动处理——
  不替用户承担这个风险。
- 远端删除同样**不执行**（那里没有回收站，删了不可恢复）。
- 删已有的东西，仍然要满足 F1 的凭据要求。

### 验收

- 本地删除后，文件能在系统回收站里找到。
- 构造一个"放不进回收站"的情形（例如超过回收站配额的目录），删除请求被拒绝且说明原因。
- 对远端路径发删除请求，被拒绝。

### 不包含

- 不做"软删除到自己的回收站目录"那套——用户的回收站才是他能自己找回来的地方。
- 不做撤销（`undo`）：删完之后没有再"恢复"的工具，回收站就是恢复手段。
- 不判断"该不该删"——那是 AI 与用户的判断，工具只负责**让误删可恢复**。

## F5 · 失败了，却看起来像成功

| | |
|---|---|
| **状态** | 已解决（`Global.cs` 的调用过滤器：异常收口 + `isError`） |
| **涉及** | 全部 MCP 项目（共享层） |

### 背景

工具"没做成"的时候，调用方需要立刻知道。**如果失败长得像成功，AI 就会基于一个没发生的事实继续往下干。**

这不是假设。别人的项目里实测过：一个工具**超时**了（`MCP error -32001: Request timed out`）却返回 `{}`，
agent 把它当成成功，接着往下走（`todo/Csharp工具痛点.md` 第七节第 5 条）。

### 现状

失败有三条路，形态各不相同：

1. **抛异常** —— MCP 只回一句 `An error occurred invoking 'x'.`，**具体原因丢掉**（工具自己写的中文提示没了）；
2. **返回错误文本** —— 内容里写着 `Error: ...`，但协议层的 `isError` 仍然是 `false`，**调用方得读文本猜**；
3. **返回空结果** —— 最糟的一种："没找到"和"没做成"长得一样，甚至和"本来就没有"也长得一样。

三条路并存，于是每个工具作者都得自己记得"我这次是哪种"。

### 期望

- **异常一律收口**：工具抛出的异常在共享层转成 `Error: ` 开头的文本 + `isError = true`，
  具体原因**保留**（不换成 SDK 那句泛泛的话）。
- **工具方法里不再自己 `try/catch` 包一层**——包了就会有人漏，漏了就是上面第 1 条。
- `Error: ` 前缀这个约定与协议层的 `isError` **对齐**：写了前缀的，`isError` 一定为真。
- **空结果必须解释为什么**：是"真的没有"，还是"被条件挡掉了"，还是"取不到"。

### 验收

- 工具里抛异常 → 调用方拿到 `Error: <具体原因>` 且 `isError = true`（不是 SDK 那句泛泛的）。
- 工具返回以 `Error: ` 开头的文本 → `isError` 被翻转成 `true`。
- 正常结果里**出现** `Error: ` 字样（例如结果里引用了一段错误文案）**不会**被误判成失败。

### 不包含

- 不做重试：失败就是失败，重不重试是调用方的判断。
- 不做错误的分类/编号体系（错误码那套），只要**原因说清楚**。
- 不管"输出内容够不够让 AI 分清成功与失败"这件事的另一半——那是各提案**设计**一节里逐条写"预期返回什么"。
